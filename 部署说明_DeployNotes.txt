=====================================================================
 llama.cpp 本地部署交付摘要（Windows 原生 / 消费级 N 卡显存混合卸载，纯 CPU 兜底）
 核心目的：让本地消费级显卡（N 卡，主目标 8 GB 显存，最低验证 3 GB）跑动 30B~35B MoE 大模型
 关键做法：显存与内存「混合」承担（非专家权重上显存、占大头的专家权重留内存），
           两边协同比纯 CPU 明显更快；没有独显或显存不够时纯 CPU 兜底照样能跑
 优先级：  实用性与 Token 生成速度优先；设计目标：尽可能达到 25 token/s
先看这个 -> 使用说明_UserGuide.md（面向使用者的安装、依赖、路径与排查说明）
 重点：AVX-512 完整启用（含 VNNI / VBMI）
=====================================================================
源码：ggml-org/llama.cpp（官方仓库 master，版本 0.6.0-dev）
硬件：AMD Ryzen 9 9950X（Zen 5，16 物理核 / 32 逻辑核）
      下位替代：Ryzen 9 7950X（16 核 32 线程、同样支持 AVX-512，配置不用改，速度略低）
      内存：64 GB DDR5-6000（2×32 GB 双通道，EXPO 已开，实际运行 6000 MT/s）
      <-- 本项目核心是「Ryzen + DDR5 内存带宽」而非某个模型，详见 README.md 第二章
      <-- 换到 Intel 平台请先看《参数阶梯手册_TierManual.md》的"平台声明"：
          无需重新编译，但档位速度表与线程数需按新 CPU 重定。
日期：2026-10-14（AVX-512 专项复核后更新）

2) 编译配置摘要
---------------------------------------------------------------------
  构建类型：      Release
  编译器：        MSVC (cl) 19.44.35225 [Visual Studio 2022 Community 17.14]
  工具链：        MSVC 14.44.35207 + Windows SDK 10.0.26100.0
  生成器：        Ninja
                  （本环境安全策略拦截 vcvarsall/MSBuild，VS 生成器不可用；
                    Ninja 调用同一 MSVC 工具链，产物等价。你本机可用
                    build-from-source.bat 以 VS 生成器重编。）

  关键配置：      GGML_CPU_ALL_VARIANTS=ON   （启用 AVX-512 扩展的唯一途径）
                  GGML_BACKEND_DL=ON         （变体以动态后端加载）
                  BUILD_SHARED_LIBS=ON
                  GGML_NATIVE=OFF            （由 ALL_VARIANTS 取代）

  启用的后端：    随包的 CPU 后端（编译期不含 GPU 后端；显存混合卸载所需的
                  ggml-cuda.dll 由用户按 README 第 3 步自取，运行时动态加载）
  关闭的后端/选项：CUDA=OFF, Vulkan=OFF, OpenCL=OFF, Metal=OFF, HIP=OFF,
                  LLAMA_OPENSSL=OFF(HTTPS), UI/预编译UI=OFF,
                  LLAMA_BUILD_TESTS=OFF, LLAMA_BUILD_EXAMPLES=OFF
  工具开关：      LLAMA_BUILD_SERVER=ON

  【为什么必须走 ALL_VARIANTS】
    ggml_add_cpu_backend_variant() 会先把所有 ISA 开关重置为 OFF 再按变体重设，
    因此命令行直接传 -DGGML_AVX512_VNNI=ON 会被冲掉，不生效；
    只有 ALL_VARIANTS 才会注册带 VNNI/VBMI 的 icelake 变体。

  【变体择优的一处上游细节】
    上游对 VBMI 只定义了 __AVX512VBMI__（启用代码路径），
    未定义参与评分的 GGML_AVX512_VBMI，导致 icelake 与 cascadelake 同分，
    而 cascadelake 按字母序先命中（不含 VBMI）。
    已用 CPUID 实测确认本机 VBMI=1（硬件支持），故将
      ggml-cpu-cascadelake.dll -> ggml-cpu-cascadelake.dll.disabled
    使 icelake（AVX-512 + VBMI + VNNI）成为最高分变体。
    此操作为改名而非删除，随时可改回。

4) 使用说明（如何调用工具，不涉及具体模型）
---------------------------------------------------------------------
  帮助 / 版本：
    E:\llm-cpp\llama.cpp\build-zen5\bin\llama-cli.exe     --help
    E:\llm-cpp\llama.cpp\build-zen5\bin\llama-server.exe  --help

  线程 / 上下文策略（重要，已由实测确定，见第 6 节）：
    本机 16 物理核 / 32 逻辑核。固定用 24 线程（实测 8~40 线程生成速度基本持平，
    瓶颈在显存/内存带宽与逐层串行，不在 CPU 算力）。
    生成速度与上下文长度几乎无关：短对话在任何档位都约 21~24 t/s（3G 卡），
    只有把上下文填满才缓降（32K 填满约 20、64K 填满 11.2）。上下文越长越慢的是 prefill。
    注意 prefill 与 decode 的瓶颈不在同一块硬件上（v0.2.8 实测）：
      decode（生成，浅上下文）CPU 24/24 线程满载 100%，GPU 只有 34~73%  → 瓶颈是 CPU
      decode（生成，64K 填满）CPU 约 64%，GPU 约 81%                   → 两边串行互相等
      prefill（读提示词）CPU 仅 3~14%，GPU 96~99%                      → 瓶颈是 GPU
    所以「CPU 没跑满」在 prefill 是常态，此时加 CPU 的活不会更快；
    深上下文 decode 时两边都吃不满，是层在显卡、专家在内存的串行依赖所致。
    提速方向：把更多权重挪到显存（减少 CPU 每 token 的搬运量），或减少每步要扫的 KV。
    64K 档实测：q8_0 KV + 40 层 = 11.3 t/s；同卡换 f16 只能上 24 层，只剩 7.5 t/s。
    档位：1=16K 2=24K 3=32K 4=64K 5=96K 6=128K（12K 太短已取消）。
      启动菜单会按显卡显存自动推荐档位（8G→64K、12G→96K、16G→128K）。
      64K 及以上在小显存卡上会自动给 KV 加 q8_0 量化。
    有 N 卡时默认启用显存混合卸载；无 N 卡按纯 CPU（约 15.6 t/s）。
    脚本已内置 THREADS=24，改 CTX 即可换档（现场在 :APPLY_TIER 段）。
    全部档位数据与取舍：E:\llm-cpp\参数阶梯手册_TierManual.md

  快捷开关（推荐，工作区根目录，全中文命名）：
    E:\llm-cpp\启动大模型_StartModel.bat              二合一开关：未运行则启动，已运行则关闭
                                        （双击即可，按提示选档位，默认实用档）
    E:\llm-cpp\启动大模型_StartModel.bat start 2      直接以实用档（16K/24 线程）启动
    E:\llm-cpp\启动大模型_StartModel.bat stop         关闭服务并释放内存
    E:\llm-cpp\启动大模型_StartModel.bat restart 3    以长文档档（24K/24 线程）重启
    E:\llm-cpp\启动大模型_StartModel.bat status       只看状态（PID / 内存 / 档位 / 地址）
    E:\llm-cpp\启动大模型_StartModel.bat check        只做环境与安全检查

    E:\llm-cpp\环境检查_EnvCheck.bat                全量体检，并给出各档位内存可行性
    E:\llm-cpp\参数阶梯手册_TierManual.md             参数阶梯手册（全部实测档位，改配置前先看它）

  启动脚本内置的检查（出现 [失败] 会直接阻止启动）：
    1  可执行程序 llama-server.exe / llama-cli.exe
    2  依赖 DLL：llama / llama-common / ggml / ggml-base
    3  CPU 后端变体：确认 icelake(AVX-512+VNNI+VBMI) 生效；
       若发现 cascadelake 抢占会自动改名为 .disabled
    4  模型文件存在且大小合理（完整约 19.8 GB）
    5  多模态投影 mmproj（缺失只警告，退化为纯文本）
    6  端口 35035 是否被别的进程占用（并打印占用者进程名）
    7  磁盘剩余空间（低于 2 GB 拒绝启动）

       GPU 不可用时只提示、不阻拦（服务仍以纯 CPU 正常运行）

  深度思考（推理链）开关 —— 除档位外对响应速度影响最大的开关：
    默认关闭。关闭时直接作答；开启时先输出一段思考内容（reasoning_content）。
    命令行：启动大模型_StartModel.bat start 2 nothink   关闭（默认）
            启动大模型_StartModel.bat start 2 think     开启
    交互模式选完档位后会询问一次，直接回车 = 关闭。
    同一问题实测（17×23=？）：
      关闭 -> 4 token、约 0.3 秒出结果
      开启 -> 241 token、约 15 秒（思考过程 492 字符）
      两者答案一致，差别只在要不要先把推理写出来，关闭可省约 98% 输出 token。
    当前生效的模式可用 启动大模型_StartModel.bat status 查看（也记录在 logs\server.pid 末位）。

  服务运行方式：无窗口静默后台运行。
    启动后不会出现任何服务窗口（任务栏也看不到），进程完全独立于脚本窗口，
    关闭启动脚本的窗口不会影响服务。日志照旧写到 logs\。
    实现方式：WScript.Shell 的 Run 以隐藏窗口风格（0）、不等待（false）拉起
    一个 cmd 包装进程完成启动与日志重定向。详见 _维护脚本\说明.md。

  GPU 混合卸载（只针对 NVIDIA 独立显卡，默认开启，CPU 兜底）：
    把「每 token 必读」的权重放进显存提速。实测本模型专家权重约占 92%
    （约 18.2 GiB）但每 token 只用 8/256：先把非专家权重（约 1.6 GiB）全放显存，
    显存还有余量就把「部分专家层」也搬上去（每层约 498 MiB）。这样同 CPU / 内存下，
    显存越大 → 上显存的专家越多 → 解码越快。
    显存实测（32K 档）：模型 1338 + KV 640 + RS 61 + 计算 476 ≈ 2515 MiB / 3071 MiB。
      - GPU_MODE=auto   默认。自动探测；先算非专家层数 N = 可给权重 ÷ GPU_LAYER_MIB
                        （=40），再把剩余显存用来上专家层：
                        E = (可给权重 - N×40) ÷ GPU_EXPERT_LAYER_MIB（=500）；
                        参数为 --n-gpu-layers N [--n-cpu-moe (40-E) | --cpu-moe] --parallel 1
                        -ub 1024 -fa on（UB 见下：实测预填充 +38%）
                        （按总显存算而不是按空闲值，因为 llama.cpp 报的 free
                          额外扣了一份保留量，用它算会少卸好几层）
      - GPU_MODE=off    强制纯 CPU（与旧版逐字节一致，仍传 --n-gpu-layers 0）
      - 命令行加 gpu / nogpu 可临时切换，不改文件，重启后回到文件设置
      - 探测用 llama-server --list-devices（后端自报，含总/空闲显存）；
        这一步会真正加载 CUDA 后端，所以它成功即代表整条链路可用
      - 不可用时自动退回纯 CPU，不阻断启动 —— 所以默认开着是安全的
      - 只支持 NVIDIA 独显：核显与 AMD / Intel 卡一律纯 CPU
      - 显存策略刻意「压满、不留余量」：标定用的 3 GB 卡是最坏情况；
        主流消费级 N 卡普遍 4 GB 起，非专家层数会被 GPU_NLAYER=40 封顶，
        本来就吃不满那约 1.6 GiB，余量天然更大。
        只有 3 GB 卡同时跑重度图形程序时可能越界分页，那就调大 GPU_SAFETY_MIB。
      - 实测收益（GTX 1060 3GB / Pascal / 16K，走本项目脚本端到端）：
          纯 CPU            生成 15.59 t/s   填满 11.55 t/s
          自动 GPU（40 层）  生成 23.73 t/s   填满 21.96 t/s   （+52% / +90%）
        卸载层数不敏感：32 层往上生成速度基本持平，压到上限即可。
        模型对比（短对话）：无 MTP 版 23.6 t/s、带 MTP 版 21.0 t/s（慢约 14%）、
                  IQ3_S 24.8 t/s —— 故本项目不再使用 MTP 模型。
      - 两个实测踩到的坑（脚本已规避，改脚本时别改回去）：
          1. --fit on 与 --cpu-moe 不能同用。--cpu-moe 会设置张量缓冲区覆盖，
             --fit 发现「用户已设置覆盖」就直接放弃（日志原文：
             failed to fit params ... tensor_buft_overrides already set by user,
             abort），随后 n_gpu_layers 落到「全部层」，把 42/42 层塞进显存，
             需求超过容量 → WDDM 分页 → 生成速度掉到 1/2.4。
          2. -nkvo（KV 留内存）会让收益归零：卸载后每 token 都要把 KV 经 PCIe
             搬回 GPU。实测加 -nkvo 后收益全部消失，与纯 CPU 持平。
      - 检测入口有两处：启动脚本第 10 项「显卡」、环境检查第 11 项
        「GPU 支持自检」。后者多一步「后端实测」—— 只有后端自己列得出
        设备，才算 llama.cpp 真能用它；前面几步只说明条件具备。
      - 手工模式里 GPU_DEVICE 若写错，会在拼参数前被预校验拦下并改回
        自动选择（llama-server 遇到无效设备名是直接报错退出，服务起不来）
      - 探测会在本控制台里跑一次 llama-server，而它会把控制台代码页改成
        UTF-8，脚本随后会立刻改回 936；否则后面所有 GBK 中文都会变乱码
    本包不含任何 CUDA 二进制（约 770 MB 的 cuBLAS 运行库 + 后端 DLL 由用户自备），
    但提供了自编脚本：_维护脚本\build-cuda-backend.bat [架构]
      - 默认架构 61（Pascal / GTX 10 系）；产物 llama.cpp\build-cuda\bin\ggml-cuda.dll
        约 32 MB，拷进 build-zen5\bin\ 即被自动加载
      - 自己编的最大好处：后端 API 版本与 llama-server 必然一致
      - 前置工具：CUDA Toolkit 12.8 + MSVC 14.44；不依赖 vcvars（本环境会被拦），
        脚本里手工拼 PATH/INCLUDE/LIB，SDK 的 bin 目录必须在 PATH 里（CMake 要用 rc.exe）
      - 注意脚本必须是纯 ASCII + CRLF，否则 cmd 按 GBK 解析会直接崩
    环境检查_EnvCheck.bat 第 11 项「GPU 支持自检」会逐条说明缺什么、怎么补。
    原理、显存预算与旧卡注意事项见 参数阶梯手册_TierManual.md 的「GPU 混合卸载」章节。

  密钥机制与安装路径（实测结论）：
    api-key.txt 支持多行，每行一个密钥（井号开头是注释），脚本会把它们用逗号
    拼接后以 --api-key 传值给服务，因此项目可以放在含中文的目录下。
    之所以不用 llama-server 的 --api-key-file：实测该参数打不开含中文的路径

6) 上下文 × 线程 矩阵基准（8 组，2026-10-15）【历史存档：纯 CPU 早期基线】
=====================================================================
  ！注意：本节是早期【纯 CPU、带 MTP 模型】的基线，已被后续改造取代。
    当前数据（无 MTP 模型 + 默认 GPU 混合卸载）见 参数阶梯手册_TierManual.md：
    短对话约 24 t/s、填满 32K 约 20 t/s。以下仅供参考线程/上下文趋势。
  目的：在"生成体感可接受"的区间内，找出每秒生成 token 最多的组合。
  方法：每次以指定 ctx / 线程重启 llama-server，把上下文填满到
        (ctx - 384 - 128)，关闭思考链，要求生成约 300 字正文，
        从服务端日志读取 prompt eval / eval 权威计时。
  原始数据：E:\llm-cpp\matrix_results.csv

  ┌────────┬────────┬──────────────┬──────────────┬─────────────┐
  │ 上下文 │ 线程   │ prefill t/s  │ 生成 t/s     │ 排名        │
  ├────────┼────────┼──────────────┼──────────────┼─────────────┤
  │  12288 │ 24     │   100.93     │  13.28 ★最优 │    1        │
  │  13312 │ 24     │    99.51     │  13.27       │    2        │
  │  12288 │ 28     │   103.12     │  13.21       │    3        │
  │  13312 │ 28     │   102.01     │  13.05       │    4        │
  │  14336 │ 24     │    99.05     │  13.05       │    4        │
  │  14336 │ 28     │   100.93     │  12.90       │    6        │
  │  16384 │ 24     │    97.09     │  12.73       │    7        │
  │  16384 │ 28     │    99.02     │  12.56       │    8        │
  └────────┴────────┴──────────────┴──────────────┴─────────────┘

  结论：
    1. 【生成速度冠军】12288 ctx + 24 线程 = 13.28 t/s
       （与末位 16384/28 的 12.56 t/s 相差 5.7%）
    2. 【线程】24 线程在 4 个上下文档位上全部优于 28 线程。
       28 线程 prefill 更快（+2%），但生成更慢——MoE 生成阶段是
       内存带宽瓶颈，线程越多争用越严重。
    3. 【上下文】生成速度随上下文单调下降：12K→16K 共损失约 4.3%。
    4. 【噪声提示】各组生成 token 数在 166~203 之间（模型自然停），
       单次测量误差约 ±0.1 t/s；24 vs 28 的差值虽小，但 4 档位方向一致，
       可判定为真实趋势而非噪声。

7) prefill 性能实测（补充：排查"首次对话慢"）
=====================================================================
  背景：出现"服务启动后第一次对话要等 1~2 分钟"的反馈，专门做了排查。

  一、先排除"冷启动惩罚"
    约 1300 token 的 prompt 实测：
      冷启动首次（新内容）：prefill 72.35 t/s（18.1 s）
      热态  （换新内容）  ：prefill 70.34 t/s（18.7 s）
    -> 两者几乎一致。不存在 mmap 导致的"首次访问磁盘"惩罚。

  二、再排查调参空间（llama-bench, pp2048）
    批大小 ubatch：512 -> 69.22 | 1024 -> 67.26 | 2048 -> 66.72   （默认已最优）
    线程数       ：16  -> 70.38 | 24   -> 68.63 | 32   -> 47.21   （32 线程劣化 31%）
    -> 默认配置就是最优点，没有可调空间。

  三、真实原因（日志实证）
    某客户端首次请求发送了 15865 token 的 prompt：
      prompt eval time = 275652.04 ms / 15865 tokens (57.55 t/s)
    prompt 几乎顶满 16K 上下文，prefill 耗时 275 秒。
    来源通常是客户端注入的超长 system prompt / 工具定义 / 知识库片段。

  四、思考模式与 prefill 无关（实测）
    同一句 hello：nothink -> prompt_tokens 13；think -> 11
    -> --reasoning 只影响生成阶段，不会撑长 prompt，也不影响 prefill。

  结论：prefill 约 70 t/s 是本机 CPU + 内存带宽的硬上限；
        "首次对话慢"由客户端 prompt 长度决定，服务端没有优化空间。
        排查方法：看 logs\ 最新日志里的 "prompt processing, n_tokens = N"。
