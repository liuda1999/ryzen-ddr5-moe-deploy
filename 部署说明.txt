2) 编译配置摘要
---------------------------------------------------------------------
  构建类型：      Release
  编译器：        MSVC (cl) 19.44.35225 [Visual Studio 2022 Community 17.14]
  工具链：        MSVC 14.44.35207 + Windows SDK 10.0.26100.0
  生成器：        Ninja
                  （本环境安全策略拦截 vcvarsall/MSBuild，VS 生成器不可用；
                    Ninja 调用同一 MSVC 工具链，产物等价。你本机可用
                    build-from-source.bat 以 VS 生成器重编。）

  关键配置：      GGML_CPU_ALL_VARIANTS=ON   （启用 AVX-512 扩展的唯一途径）
                  GGML_BACKEND_DL=ON         （变体以动态后端加载）
                  BUILD_SHARED_LIBS=ON
                  GGML_NATIVE=OFF            （由 ALL_VARIANTS 取代）

  启用的后端：    仅 CPU（无任何 GPU 后端）
  关闭的后端/选项：CUDA=OFF, Vulkan=OFF, OpenCL=OFF, Metal=OFF, HIP=OFF,
                  LLAMA_OPENSSL=OFF(HTTPS), UI/预编译UI=OFF,
                  LLAMA_BUILD_TESTS=OFF, LLAMA_BUILD_EXAMPLES=OFF
  工具开关：      LLAMA_BUILD_SERVER=ON

  【为什么必须走 ALL_VARIANTS】
    ggml_add_cpu_backend_variant() 会先把所有 ISA 开关重置为 OFF 再按变体重设，
    因此命令行直接传 -DGGML_AVX512_VNNI=ON 会被冲掉，不生效；
    只有 ALL_VARIANTS 才会注册带 VNNI/VBMI 的 icelake 变体。

  【变体择优的一处上游细节】
    上游对 VBMI 只定义了 __AVX512VBMI__（启用代码路径），
    未定义参与评分的 GGML_AVX512_VBMI，导致 icelake 与 cascadelake 同分，
    而 cascadelake 按字母序先命中（不含 VBMI）。
    已用 CPUID 实测确认本机 VBMI=1（硬件支持），故将
      ggml-cpu-cascadelake.dll -> ggml-cpu-cascadelake.dll.disabled
    使 icelake（AVX-512 + VBMI + VNNI）成为最高分变体。
    此操作为改名而非删除，随时可改回。

6) 上下文 × 线程 矩阵基准（8 组，2026-10-15）
=====================================================================
  目的：在"生成体感可接受"的区间内，找出每秒生成 token 最多的组合。
  方法：每次以指定 ctx / 线程重启 llama-server，把上下文填满到
        (ctx - 384 - 128)，关闭思考链，要求生成约 300 字正文，
        从服务端日志读取 prompt eval / eval 权威计时。
  原始数据：E:\llm-cpp\matrix_results.csv

  ┌────────┬────────┬──────────────┬──────────────┬─────────────┐
  │ 上下文 │ 线程   │ prefill t/s  │ 生成 t/s     │ 排名        │
  ├────────┼────────┼──────────────┼──────────────┼─────────────┤
  │  12288 │ 24     │   100.93     │  13.28 ★最优 │    1        │
  │  13312 │ 24     │    99.51     │  13.27       │    2        │
  │  12288 │ 28     │   103.12     │  13.21       │    3        │
  │  13312 │ 28     │   102.01     │  13.05       │    4        │
  │  14336 │ 24     │    99.05     │  13.05       │    4        │
  │  14336 │ 28     │   100.93     │  12.90       │    6        │
  │  16384 │ 24     │    97.09     │  12.73       │    7        │
  │  16384 │ 28     │    99.02     │  12.56       │    8        │
  └────────┴────────┴──────────────┴──────────────┴─────────────┘

  结论：
    1. 【生成速度冠军】12288 ctx + 24 线程 = 13.28 t/s
       （与末位 16384/28 的 12.56 t/s 相差 5.7%）
    2. 【线程】24 线程在 4 个上下文档位上全部优于 28 线程。
       28 线程 prefill 更快（+2%），但生成更慢——MoE 生成阶段是
       内存带宽瓶颈，线程越多争用越严重。
    3. 【上下文】生成速度随上下文单调下降：12K→16K 共损失约 4.3%。
    4. 【噪声提示】各组生成 token 数在 166~203 之间（模型自然停），
       单次测量误差约 ±0.1 t/s；24 vs 28 的差值虽小，但 4 档位方向一致，
       可判定为真实趋势而非噪声。

7) prefill 性能实测（补充：排查"首次对话慢"）
=====================================================================
  背景：出现"服务启动后第一次对话要等 1~2 分钟"的反馈，专门做了排查。

  一、先排除"冷启动惩罚"
    约 1300 token 的 prompt 实测：
      冷启动首次（新内容）：prefill 72.35 t/s（18.1 s）
      热态  （换新内容）  ：prefill 70.34 t/s（18.7 s）
    -> 两者几乎一致。不存在 mmap 导致的"首次访问磁盘"惩罚。

  二、再排查调参空间（llama-bench, pp2048）
    批大小 ubatch：512 -> 69.22 | 1024 -> 67.26 | 2048 -> 66.72   （默认已最优）
    线程数       ：16  -> 70.38 | 24   -> 68.63 | 32   -> 47.21   （32 线程劣化 31%）
    -> 默认配置就是最优点，没有可调空间。

  三、真实原因（日志实证）
    某客户端首次请求发送了 15865 token 的 prompt：
      prompt eval time = 275652.04 ms / 15865 tokens (57.55 t/s)
    prompt 几乎顶满 16K 上下文，prefill 耗时 275 秒。
    来源通常是客户端注入的超长 system prompt / 工具定义 / 知识库片段。

  四、思考模式与 prefill 无关（实测）
    同一句 hello：nothink -> prompt_tokens 13；think -> 11
    -> --reasoning 只影响生成阶段，不会撑长 prompt，也不影响 prefill。

  结论：prefill 约 70 t/s 是本机 CPU + 内存带宽的硬上限；
        "首次对话慢"由客户端 prompt 长度决定，服务端没有优化空间。
        排查方法：看 logs\ 最新日志里的 "prompt processing, n_tokens = N"。
