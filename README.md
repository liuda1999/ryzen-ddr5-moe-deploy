# Qwen3.6-35B-A3B 本地大模型 · 纯 CPU 一键部署包

> 在 **Windows + 纯 CPU + 无显卡** 的机器上，把 35B 级 MoE 大模型跑成随时可用的本地服务。
> 双击一个 `.bat` 就能启动，自带 OpenAI 兼容 API 与网页对话界面。

## 一、这是什么

一套围绕 [llama.cpp](https://github.com/ggml-org/llama.cpp) 封装的中文部署套件，
把「编译 → 调参 → 启停 → 鉴权 → 局域网开放」这些零散环节收成一个双击即用的项目。

它不是一个新推理引擎，而是**把 llama.cpp 在纯 CPU 上跑到可用的全部工程细节固化下来**：
编译哪些 CPU 指令集变体、线程数给多少、上下文开多大、内存够不够、模型放哪、
密钥怎么给、局域网怎么开——都已经调好并实测过，你只需要双击。

### 亮点

| | |
|---|---|
| **零依赖** | VC++ 运行时已随包附带（App-local 部署），目标机**不用装** VS / CUDA / Python / 任何运行库 |
| **免显卡** | 纯 CPU + 内存推理，`--n-gpu-layers 0` |
| **一个脚本管启停** | `启动大模型.bat` 未运行时启动、已运行则关闭；内置 9 项环境与安全检查 |
| **真就绪判定** | 不是「端口一监听就报成功」，而是轮询 `/health` 返回 200（模型真正加载完）才算成功 |
| **无窗口运行** | 服务完全静默跑在后台，任务栏不出现多余窗口 |
| **自动密钥** | 首次启动自动生成访问密钥，启动时打印并复制到剪贴板 |
| **深度思考开关** | 可一键关掉思维链。同样的题，输出 token 从 241 降到 **4** |
| **内存预检** | 按实际可用内存判断本档位能不能跑，不够就当场拦住并给出替代档位 |
| **中文路径可用** | 中文目录、中文用户名下均已实测通过 |

## 二、运行环境要求

| 项目 | 要求 |
|---|---|
| 系统 | Windows 10 / 11 **x64** |
| 内存 | **≥ 32 GB**（推荐 64 GB；默认档位需约 30 GB 可用内存） |
| 磁盘 | Q4_K_XL 约 **25 GB**；改用 IQ3_S 约 **17 GB** |
| 显卡 | **不需要**，核显独显都不用 |
| 运行时 | **什么都不用装**。VC++ 运行库已随包附带，PowerShell / curl 系统自带 |
| CPU | x86-64 即可。**支持 AVX-512 的 CPU 更快**，不支持会自动回退 AVX2 变体 |

### 平台声明（换 CPU 请先读）

本包在 **AMD Ryzen 9 9950X**（Zen 5，16 物理核 / 32 逻辑核，61.6 GB 内存）上编译与实测，
运行时会命中 `ggml-cpu-icelake.dll`（AVX-512 + VNNI + VBMI）。

- **换到别的 CPU 不需要重新编译**。包里编译了全部 9 个 CPU 变体，运行时自动择优。
- **但下面的档位速度表要重新测**。Intel 12/13/14 代消费级酷睿不支持 AVX-512，
  会回退到 AVX2 变体，速度明显低于表中数值。
- **线程数要按物理核重定**。表中 24 线程是按 16 物理核（取 12 核）定的；
  8 核 CPU 应改用 12 线程左右。详见表后说明。
- 若换到「支持 AVX-512 但不支持 VBMI」的 Intel（如 Cascade Lake 至强），
  需要把 `ggml-cpu-cascadelake.dll.disabled` 改回 `.dll`。

## 三、快速开始（三步）

### 第 1 步：拿到本包

方式 A —— 直接下载免安装包（推荐，已含编译好的程序）：

到 [Releases](../../releases) 页面下载 `...-no-model.zip`，解压到任意目录（**建议英文路径**）。

方式 B —— 克隆仓库：

```bat
git clone https://github.com/liuda1999/qwen3.6-35b-a3b-cpu-deploy.git
```

### 第 2 步：下载模型

仓库不含模型，请按 [`llama.cpp\models\下载模型.md`](llama.cpp/models/下载模型.md) 下载，
放进 `llama.cpp\models\` 目录。

### 第 3 步：双击启动

双击 **`启动大模型.bat`**，回答两个问题：

1. **选配置档位** —— 直接回车 = 档位 2（16K 上下文 / 24 线程，实用档）
2. **是否开启深度思考** —— 直接回车 = 关闭（更快、更省 token）

约 15~30 秒后显示「启动成功」并打印本次 API 信息，浏览器打开提示的地址即可对话。

> **同一个脚本再运行一次就是关闭服务**（自动释放内存）。
> 想确认服务在不在：`启动大模型.bat status`。

## 五、配置档位（实测数据）

以下均为本机（Ryzen 9 9950X / 61.6 GB）实测，**上下文越大生成越慢、内存越多**：

| 档位 | 上下文 | 线程 | 生成速度 | 约需内存 | 适用场景 |
|---|---|---|---|---|---|
| 1 极速档 | 12288（12K） | 24 | **13.28 t/s** | 28 GB | 短问答、追求最快 |
| **2 实用档（默认）** | **16384（16K）** | **24** | **12.73 t/s** | **30 GB** | 日常对话 + 中等长度文档 |
| 3 长文档档 | 24576（24K） | 24 | 11.82 t/s | 34 GB | 长文档分析 |
| 4 超长档 | 32768（32K） | 24 | 9.95 t/s | 38 GB | 超长上下文 |
| 5 极限档 | 65536（64K） | 28 | 4.28 t/s | 55 GB | 能跑，但很慢 |

**三条实测规律**（选档位时照着套）：

1. **24 线程在所有档位都比 28 线程快**。MoE 解码是内存带宽瓶颈，线程越多争用越严重。
2. **速度取决于实际填充的上下文长度，不是分配的 `-c` 值**。同样 16K 档位，
   短提示（33 token）能跑到 **16.06 t/s**。
3. **prefill（读提示）约 70 token/秒是硬上限**，与线程数、批大小基本无关
   （实测 16 线程 70.4 / 24 线程 68.6 / 32 线程 47.2 t/s；`--ubatch-size` 加大反而变慢）。
   所以**首次对话等多久，取决于客户端发了多长的提示**——
   若客户端注入了上万个 token 的系统提示词 / 工具定义，等 3 分钟是正常的，不是卡死。

完整实测记录（含 12 个测试点、内存换算、平台差异）见 [`参数阶梯手册.md`](参数阶梯手册.md)。

## 六、深度思考开关

选完档位后会问一次，**直接回车 = 关闭**。也可用命令行指定：

```bat
启动大模型.bat start 2 nothink    :: 关闭（默认）
启动大模型.bat start 2 think      :: 开启
```

同一个问题（「17×23=？」）、同一档位的实测对比：

| 模式 | 输出 token | 出结果耗时 |
|---|---|---|
| **关闭（默认）** | **4** | **约 0.3 秒** |
| 开启 | 241 | 约 15 秒 |

答案完全一样。差别只在要不要先把整段推理过程写出来——关闭后**省掉约 98% 的输出 token**。

> 服务端用的是 llama.cpp 的 `--reasoning off`，对 prompt 长度几乎无影响
> （实测 13 token vs 11 token），只影响生成阶段。

## 七、API 使用

服务是 **OpenAI 兼容**接口，端口固定为 **35035**（刻意避开 8080 / 8000 / 11434 等常用端口）。

| 用途 | 地址 |
|---|---|
| 网页对话控制台 | `http://127.0.0.1:35035` |
| OpenAI 兼容 API | `http://127.0.0.1:35035/v1` |

启动成功后窗口会打印**本次服务 API**（含地址与密钥），密钥同时复制到剪贴板。

```bat
curl -H "Authorization: Bearer <你的密钥>" ^
     http://127.0.0.1:35035/v1/chat/completions ^
     -H "Content-Type: application/json" ^
     -d "{\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}]}"
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:35035/v1",
                api_key="<你的密钥>")
```

**密钥填写要点**（这几条踩过坑）：

- 密钥存在项目根目录 `api-key.txt`，**每台机器首次启动自动生成**；
- 区分大小写，**不要加 `sk-` 前缀**，不要留空；
- 服务端**只认请求头**（`Authorization: Bearer`），**不支持** `?api_key=` 这种拼在 URL 上的写法；
- 客户端「模型名」留空或随便填即可（单模型服务）。

### 局域网访问

启动脚本默认 `HOST=0.0.0.0`，即局域网内其它设备可以访问（**需携带密钥**）。

```bat
:: 1) 以管理员身份运行一次，放行防火墙入站端口
开放局域网端口.bat

:: 2) 其它设备用局域网地址访问
http://<本机局域网IP>:35035
```

> ⚠️ **安全提示**：放行后，同网段**任何拿到密钥的设备**都能占用你的 CPU 和内存做推理
> （默认档位单次约 30 GB）。在咖啡厅、酒店等不可信 Wi-Fi 下，建议改成仅本机：
> 把 `启动大模型.bat` 里的 `set "HOST=0.0.0.0"` 改回 `set "HOST=127.0.0.1"` 后重启。
>
> 放行脚本用的是 `netsh advfirewall`，会对**所有网络配置文件**（域/专用/公用）生效，
> 且规则**不随项目删除而消失**，需要时用同一脚本的选项 2 撤销。

## 九、目录结构

```
.
├── 启动大模型.bat          ← 主入口：二合一开关（未运行则启动，已运行则关闭）
├── 环境检查.bat            ← 10 项环境与安全体检，启动前自查
├── 开放局域网端口.bat       ← 放行防火墙入站端口（需管理员运行一次）
├── 重新编译.bat            ← 从源码重新编译（需 Visual Studio）
├── 使用说明.md / 参数阶梯手册.md / 部署说明.txt / 验收报告.md
├── 分发包清单.txt           ← 完整性校验清单
├── _维护脚本\               ← 脚本生成器与维护工具（改 bat 请改这里）
└── llama.cpp\              ← llama.cpp 源码 + 编译产物 + 模型目录
    ├── build-zen5\bin\      ← 运行所需的 exe / dll（含 9 个 CPU 变体与 VC++ 运行时）
    └── models\              ← 模型放这里（.gguf 不进仓库）
```

**为什么要提供 `_维护脚本\`**：所有 `.bat` 都是 GBK + CRLF 编码的，
**用记事本直接改会破坏编码导致中文乱码**。正确做法是改生成器再重新生成：

```bat
python _维护脚本\gen_toggle.py    :: 重新生成 启动大模型.bat
python _维护脚本\gen_check.py     :: 重新生成 环境检查.bat
```

## 十、已知限制

1. **仅 Windows x64**。脚本是 `.bat`，依赖 `cmd.exe` 与 PowerShell。
2. **首次对话可能很慢**。服务端 prefill 约 70 token/秒；如果客户端注入了
   上万 token 的系统提示词或工具定义，光读提示就要几分钟。
   排查方法：看 `logs\` 里最新日志的 `n_tokens =` 数值。
3. **无 GPU 加速**。纯 CPU 推理，生成速度约 13 t/s，不适合高并发。
4. **单模型服务**。同时只服务一个模型，不排队、不调度。
5. **档位速度表是特定硬件实测值**。换 CPU、换模型量化级别后需重测。
6. **中文路径可用，但仍建议英文路径**。llama.cpp 的 `--api-key-file` 打不开中文路径
   （本包已改为传密钥值而非文件路径来规避），且英文路径在第三方工具兼容性上更省心。
