# 消费级显卡跑 30B\~35B MoE 大模型 · 本地 AI 服务部署与调优套件

> **核心目的**：让**消费级显卡** —— 那些 **4 GB / 8 GB / 12 GB** 的普通家用、游戏显卡 ——
> 跑动 **30B\~35B 的 MoE 架构大模型**，在本机拥有一套**随时可用的本地 AI 服务**。
> 不租云、不买专业卡、数据不出本机。
>
> **关键做法**：**显存与内存「混合用」** —— 每 token 必读的非专家权重放显存，
> 剩余显存继续把**专家层**也搬上显存，占大头的专家权重留内存；没有独显时纯 CPU 兜底。
>
> **优先级**：**实用性与生成速度优先**。设计目标 25 token/s；标定卡 GTX 1060 3GB 实测 **22\~24 t/s**。

> **【重要前提】本项目优化的是 Q4 级量化的 MoE 模型，不是 Q2 / IQ2 的“极限压缩”版。**
>
> 全套标定（显存预算、卸载层数、速度与上下文结论）都以 **Q4_K_M / IQ3_S 这类 4-bit 级量化** 为基准。
> **不要把模型换成 Q2_K / IQ2_S 等 2-bit 级量化** —— 它们虽然也“跑得起来”，但输出质量与 Q4 级
> **差着天壤之别**：这是量化位宽本身造成的差距，不是调参能弥补的。本项目不针对、也不推荐低比特量化。

## 一、这是什么

把 llama.cpp 封装成**双击即用**的本地 MoE 推理套件：模型下载、显存预算、指令集变体、内存带宽、
线程与上下文标定、启停、鉴权、局域网开放 —— 全部固化好并实测过。

**为什么消费级显卡跑得动 35B**：MoE 每个 token 只激活少数专家（本模型 256 选 8），
显存不必装下全部 35B，只需装下**每 token 都要读的那部分**，其余专家按需从内存取。

| 亮点 | 说明 |
|---|---|
| **免装运行库** | VC++ 运行时随包附带（App-local），不装 VS / CUDA / Python |
| **显存 + 内存混合** | **3 GB 最低验证、4 GB 起宽裕**（4 / 8 / 12 GB 是主力区间）就能跑 30B\~35B；层数与专家卸载按显存自动算；无 N 卡自动纯 CPU |
| **一个脚本管启停** | 未运行则启动、已运行则关闭；内置 10 项环境与安全检查 |
| **真就绪判定** | 轮询 `/health` 返回 200（模型真加载完）才算成功，不是“端口通了就报成功” |
| **启动即预热** | 就绪后先发一个真实小请求，首次对话不再等首字 |
| **自动密钥 + 局域网** | 首次启动生成密钥、打印并复制到剪贴板；可选放行防火墙供局域网使用 |
| **视觉 / 深度思考开关** | mmproj 可选载入；思考链可一键关闭（同题 241 → 4 token） |
| **模型可替换** | 换 `.gguf` 改一行即可，套件不与模型绑定；内置 IQ3_S / Q4_K_M 下载 |

> **当前实例**：`Qwen3.6-35B-A3B-UD-Q4_K_M.gguf`（MoE 256 选 8，**无 MTP**，20.61 GB）。
> **本项目不使用带 MTP 的模型** —— 实测同规格带 MTP 版即使不开投机也慢约 14%。

## 二、原理与实测规律

### 2.1 一句话原理

MoE 每 token 只读少数专家，算术强度低，瓶颈是**内存能把权重喂多快**：

```
生成速度 ≈ 内存带宽 ÷ 每 token 需要读取的字节数
```

所以调优主线是**内存带宽**（DDR5 + EXPO + 双通道），不是核心数或算力。

### 2.2 三条实测规律

1. **24 线程比 28 线程快**（所有档位）：解码阶段带宽已打满，多线程只是抢同一条总线。
2. **prefill（读提示）有固定上限**：加线程、加批大小都突破不了（`-ub` 只在 512 → 1024 这一段有效，见「0.3.1 主要更新」）。
3. **生成速度取决于「实际填了多少上下文」，不是档位 `-c` 值**：同档位短提示 22 t/s、填满 62K 只有 11 t/s。

### 2.3 硬件基准与 EXPO 自查

| 项目 | 实测值 |
|---|---|
| CPU | Ryzen 9 9950X（Zen 5，16C/32T，命中 AVX-512 + VNNI + VBMI 变体）；**下位替代 7950X**（Zen 4，16C/32T，配置不用改，速度略低） |
| 内存 | 2 × 32 GB = 64 GB **双通道**，DDR5-6000 CL36 |
| 当前频率 | **6000 MT/s（EXPO 已生效）**；JEDEC 默认只有 4800 |

**EXPO 是必开项**：4800 → 6000 是 **+25% 带宽**，在带宽瓶颈的解码阶段几乎线性收益。
自查：任务管理器 → 性能 → 内存 → 右下角「速度」；显示 4800 就是没开。

```powershell
Get-CimInstance Win32_PhysicalMemory |
  Select-Object DeviceLocator, Capacity, Speed, ConfiguredClockSpeed, PartNumber
```

### 2.4 换平台会怎样

| 情况 | 影响 |
|---|---|
| 不开 EXPO（4800） | 带宽 −20%，速度大致等比下降 |
| 只插单条内存 | 带宽腰斩，速度近乎腰斩（**双通道是硬前提**） |
| Intel 12/13/14 代酷睿 | 无 AVX-512，自动回退 AVX2，明显更慢 |
| 换密集（非 MoE）模型 | 每 token 读全部权重，带宽压力成倍上升 |

> 换 CPU **不需要重新编译**：包里编译了全部 9 个指令集变体，运行时自动择优；但速度表需重测。

## 三、运行环境要求

| 项目 | 要求 |
|---|---|
| 系统 | Windows 10 / 11 **x64** |
| CPU | **AMD Ryzen 推荐**（本包在 9950X 标定；无 9950X 可用 **7950X** 替代，配置不用改）；支持 AVX-512 更快 |
| 内存 | **最低 16 GB** → IQ3_S；**推荐 32 GB 双通道** → Q4_K_M |
| 磁盘 | 约 **22 GB**（Q4_K_M 20.6 + 视觉投影 0.84 + 程序）；IQ3_S 约 **14 GB** |
| 显卡 | **可选**：NVIDIA 独显自动启用混合卸载（主力 **4 / 8 / 12 GB**，16 GB 更宽裕）；核显与 A/I 卡按纯 CPU |
| 运行时 | **什么都不用装**（VC++ 运行库随包，PowerShell / curl 系统自带） |

### 3.1 怎么按内存 / 显存选

**内存决定「装不装得下」，显存决定「跑多快、上下文多大」。**

| 内存 | 选这个量化 | 粗算需求 | 档位上限 |
|---|---|---|---|
| **16 GB** | **IQ3_S**（12.74 GB） | 13 + 1 + 2 = **16 GB** | **64K** |
| **32 GB 双通道** | **Q4_K_M**（20.61 GB） | 21 + 1 + 2 = **24 GB**，96K 需 25、160K/192K 需 26 | **96K\~192K**（随显存） |
| **64 GB 及以上** | Q4_K_M 及以上 | 内存不再是瓶颈 | **192K**，上限改由显存决定 |

| 显存 | 短对话生成 | 建议档位 | 备注 |
|---|---|---|---|
| 无独显 / 核显 / A·I 卡 | 约 **15.6 t/s** | **32K 起** | 纯 CPU 兜底，永远可用 |
| **3 GB**（GTX 1060） | **22\~24 t/s** | **64K**（自动加 q8_0 KV） | 标定卡；填满 62K 约 11 t/s |
| **4 GB** | 约 22 t/s（估） | **64K** | 静态 37 层；96K 起自动关视觉塔换层数 |
| **8 GB** | ≈40 t/s（估） | **96K**（可选 64\~96K） | 现代卡外推值 |
| **12 GB** | 50\~60 t/s（估） | **128K**（可选 96\~128K） | 现代卡外推值 |
| **16 GB** | 70\~80 t/s（估） | **160K**（可选 128\~160K） | 现代卡外推值 |
| 24 GB 及以上 | — | **192K** | 层数与专家全上显存 |

> 显存越大越快的原因：非专家权重压满 40 层后，**剩余显存继续把专家层搬上显存**
> （`--n-cpu-moe K`，显存越大 K 越小）。8 / 12 / 16 GB 在各自推荐档位（96K / 128K / 160K）
> 约对应 **7 / 14 / 22 层**专家（`check_budget.py` 2026-10-17 实跑值）。

## 四、快速开始

**第 1 步 · 拿包**：到 [Releases](../../releases) 下载 `...-no-model.zip` 解压（建议英文路径）。
包内含程序与文档，**不含模型**（20.8 GB），也**不含 CUDA 后端**（可选，见下）。
或 `git clone https://github.com/liuda1999/ryzen-ddr5-moe-deploy.git`。

**第 2 步 · 双击 `启动大模型_StartModel.bat`**，首次会依次：

1. **环境与安全检查**（10 项，有失败直接拦住，最后报出显卡与显存）；
2. **检查模型** —— 没有就问你要 `1=IQ3_S / 2=Q4_K_M`，用系统 `curl` **断点续传**下载，已有则跳过；
3. **选档位** —— 直接回车用推荐值；
4. **深度思考** —— 直接回车 = 关闭（更快）。

约 30\~90 秒后显示「启动成功」并打印 API 信息，浏览器打开即可对话。

```bat
启动大模型_StartModel.bat            :: 再运行一次 = 关闭服务（释放内存）
启动大模型_StartModel.bat menu       :: 重启 / 打开网页 / 查看日志
启动大模型_StartModel.bat status     :: 看服务状态与当前档位
```

**第 3 步 · NVIDIA 独显加速（默认开启，无需配置）**

```bat
启动大模型_StartModel.bat start 2 nothink nogpu   :: 临时关掉做对比
:: 长期关掉：把脚本顶部 GPU_MODE 改成 off
```

| GPU 加速需要 | 说明 |
|---|---|
| NVIDIA 显卡驱动 | 机器本来就有 |
| **CUDA 运行库**（3 个 DLL，≈770 MB） | **不随驱动安装**；复用本机已有 CUDA / PyTorch 的最省事，加进 `PATH` |
| **CUDA 后端** `ggml-cuda.dll` | 从 llama.cpp 官方 Windows CUDA 预编译包取出，放进 `llama.cpp\build-zen5\bin\` |

`环境检查_EnvCheck.bat` 第 11 项会逐条告诉你缺什么。两个前提：**必须 CUDA 12.x**；
后端 **API 版本须与本项目一致（当前 3）**，否则拒绝加载并**自动退回纯 CPU**（安全失败，不崩溃）。

## 六、档位与速度

启动脚本按显存自动推荐档位（直接回车即用）。**档位只决定上下文上限，速度看实际填充量。**

| 档位 | 上下文 | 输出建议 max_tokens | 建议显存 | 需内存 IQ3_S / Q4_K_M | 3 GB 标定卡层数 |
|---|---|---|---|---|---|
| **1 短任务档** | **32K** | 8192 | 无 N 卡 / ≤4 G | 16 / 24 GB | **40** |
| 2 中档 | 48K | 12288 | ≤4 G | 16 / 24 GB | 39 |
| **3 标准档** | **64K** | 16384 | **4 G** | 16 / 24 GB | 35 |
| 4 长文档档 | 96K | 24576 | **8 G** | 17 / 25 GB | 27 |
| 5 超长档 | 128K | 32768 | **12 G** | 17 / 25 GB | 19 |
| 6 长上下文档 | 160K | 40960 | **16 G** | 18 / 26 GB | 10 |
| 7 极限档 | 192K | 49152 | 24 G 及以上 | 18 / 26 GB | 见下 |

> **层数一列是 `check_budget.py` 的静态计算值**（3 GB 卡、桌面占 300 MiB、Q4_K_M、`-ub 1024`）。
> 其它容量：**4 GB → 64K 档 37 层**；**8 GB → 96K 档 40 层 + 7 层专家上显存**；
> **12 GB → 128K 档 40 层 + 14 层专家**；**16 GB → 160K 档 40 层 + 22 层专家**。
>
> **3 GB 卡在 160K / 192K 档只剩 10 层 / 2 层**，低于 8 层时脚本会自动退回纯 CPU 并明确提示
> 「本档位上下文所需的 KV 把显存占满」——这不是故障，选小一档即可。

> **32K / 64K 有实测，48K 与 96K 以上属外推**：64K 档填 32.6K 时实测
> **prefill 205.4 t/s / decode 13.27 t/s**（0.3.1 三轮连续对话 + 锚点检索通过）。
> 更长的档位按实测规律推算 —— **每多填 1 千 token，单 token 慢约 0.67 µs**
> （3.3K→21.3、29.9K→15.45、62.4K→11.27 t/s），据此 96K 约 9、128K 约 8 t/s，**属估算**。
> 旧档位实测仍可对照：6K 填充 21.2 / 16K 18.5 / 20K 17.8 / 30K 12.8（29 层）。

**必读的五条：**

- **档位只决定上限，速度看实际填了多少**：同一台机器 64K 档，填 3 万在 40 层时 15.5 t/s、29 层时 12.8；
  填 6 万约 11.3（每千 token 约 +0.67 µs）。看真实填充量请读日志 `prompt eval time` 行的 token 数。
- **prefill 与 decode 是两个瓶颈**：prefill 卡 GPU（约 240 t/s，CPU 只有个位数占用）；
  decode 在浅上下文卡 CPU（24 线程跑满），**填满后两边都不满**（CPU 约 64% / GPU 约 81%，串行互相等）。
- **显存被桌面抢走直接掉层数**：桌面占 260 MiB 时 64K 能上 40 层（21.3 t/s），占 644 MiB 只剩 21 层（11 t/s 级）。
  感觉变慢先关浏览器/视频再启动，启动信息里的「显存预算」行会打印每次的实际分配。
- **视觉塔实吃约 930 MiB**（≈23 层权重）：显存紧张时 auto 会自动不载并说明；要看图把 `MMPROJ_SW` 设为 `on`。
- **KV 精度按预算自动定**：f16 装不下就切 q8_0（32K 省约 320 MiB，代价约 0.7%）。
  8/12/16 GB 固定 q8_0 + 视觉塔常驻，为的是高上下文留余量。

## 七、深度思考开关

```bat
启动大模型_StartModel.bat start 2 nothink    :: 关闭（默认）
启动大模型_StartModel.bat start 2 think      :: 开启
```

同一题（17×23）、同档位实测：

| 模式 | 输出 token | 耗时 |
|---|---|---|
| **关闭（默认）** | **4** | **约 0.3 秒** |
| 开启 | 241 | 约 15 秒 |

答案相同，关闭省掉约 **98%** 输出 token。服务端用 `--reasoning off`，只影响生成阶段，
对 prompt 长度几乎无影响（13 vs 11 token）；不支持思考链的模型无副作用。

## 八、API 使用

OpenAI 兼容，端口固定 **35035**（刻意避开 8080 / 8000 / 11434）。

| 用途 | 地址 |
|---|---|
| 网页控制台 | `http://127.0.0.1:35035` |
| OpenAI 兼容 API | `http://127.0.0.1:35035/v1` |

启动成功会打印地址与密钥，并复制密钥到剪贴板。

```bat
curl -H "Authorization: Bearer <你的密钥>" ^
     http://127.0.0.1:35035/v1/chat/completions ^
     -H "Content-Type: application/json" ^
     -d "{\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}]}"
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:35035/v1", api_key="<你的密钥>")
```

**密钥要点**：存在 `api-key.txt`，首次启动自动生成；**区分大小写、不要加 `sk-` 前缀**；
**只认请求头** `Authorization: Bearer`，不支持 `?api_key=`；客户端「模型名」留空即可。

**`max_tokens` 填多少**：上限 = 当前档位 ctx − 实际输入 token。脚本每个档位都给了参考值
（= ctx ÷ 4，显示在档位菜单与启动信息里）：

| 档位 | 32K | 48K | 64K | 96K | 128K | 160K | 192K |
|---|---|---|---|---|---|---|---|
| 建议 `max_tokens` | 8192 | 12288 | 16384 | 24576 | 32768 | 40960 | 49152 |

> 开思考时思考 token 也算在输出预算里，太小会只吐思考过程就被截断（`finish_reason=length`）。
> 填得比剩余上下文还大不会报错，服务端按剩余量截断。

### 局域网访问

```bat
:: 管理员身份运行一次，放行防火墙入站端口
开放局域网端口_OpenLanPort.bat
:: 其它设备用 http://<本机局域网IP>:35035 访问（需带密钥）
```

> ⚠️ 放行后同网段**任何拿到密钥的设备**都能占用你的 CPU 与内存。不可信 Wi-Fi 下建议把脚本里
> `HOST=0.0.0.0` 改回 `127.0.0.1`。规则用 `netsh advfirewall` 对**所有网络配置文件**生效，
> 且**不随项目删除而消失**，撤销用同一脚本的选项 2。

## 十、已知限制

1. **仅 Windows x64**（`.bat` + PowerShell）。
2. **首次对话可能很慢**：客户端注入上万 token 的系统提示/工具定义时，光读提示就要几分钟。
   排查看 `logs\` 最新日志的 `n_tokens =`。
3. **没有 N 卡按纯 CPU**：约 15.6 t/s，不适合高并发。
4. **GPU 混合卸载只支持 NVIDIA 独显**，且默认开启；需自备 CUDA 运行库与 `ggml-cuda.dll`。
   缺它一律纯 CPU，不影响使用。公开发行包**刻意不带**后端（项目自编版只含 sm_61 Pascal 机器码）。
   显存一旦越界会 WDDM 分页暴跌（实测多放 1 层：23.9 → **6.15 t/s**）——**宁可少放几层**。
5. **96K 及以上档位本机未实测**（3 GB 卡最高只能实测到 64K，已实测通过）；更高档位的参数合法性由静态预算矩阵（9 卡 × 7 档）验证，速度数据属外推。
6. **单模型服务**，不排队、不调度；`--parallel 1` 下并发请求会**排队**（实测长请求 10 s 时短问纯等 9.6 s）。
7. **档位速度是特定硬件实测值**，换 CPU / 内存频率 / 量化级别后需重测。
8. **内置下载需要系统 `curl`**（Win10 1803+ 自带）；检测不到就提示手动下载，不卡启动。
9. **中文路径可用，仍建议英文路径**（已规避 `--api-key-file` 的中文路径问题）。
10. **内存带宽是天花板**：想更快只能加带宽（更高频 DDR5 / 双通道双 rank），调线程与批大小已到极限。
