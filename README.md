# 消费级显卡跑动 30B~35B MoE 大模型 · 本地部署与调优套件

> **核心目的**：让本地**消费级显卡**（NVIDIA 独显，**以 8 GB 显存为主目标**，最低验证到 3 GB）
> 跑动 **MoE 架构的 30B~35B 大模型**，做成随时可用的本地服务。
>
> **优先级**：**实用性与 Token 生成速度优先** —— 宁可少开一点上下文，也要保证对话时
> 「字出得快」、随手可用。
>
> **设计目标**：生成速度**尽可能达到 25 token/s**。标定卡 GTX 1060 3GB 已实测
> 24 t/s （32K 长生成实测 23.5 t/s），
> 8 GB 级现代显卡预估 40 t/s 以上。
>
> 实现路径是**显存混合卸载 + 内存带宽工程**：把「每 token 必读」的非专家权重放显存、
> 占大头的 MoE 专家权重留内存（每 token 只激活 8/256），再叠上 EXPO 内存频率、
> CPU 指令集变体、线程数与上下文大小的实测标定。**模型可替换** —— 套件不绑定任何特定模型。

## 一、这是什么

一套围绕 [llama.cpp](https://github.com/ggml-org/llama.cpp) 封装的**本地 MoE 推理部署套件**，
把「模型下载 → 显存混合卸载 → 指令集变体选择 → 内存带宽调优 → 启停 → 鉴权 → 局域网开放」
这些零散环节收成一个双击即用的项目。

它不是一个新推理引擎，而是把**「让消费级显卡把 30B~35B MoE 模型跑到可用速度」的全部工程细节固化下来**：
显存里放哪一部分权重、CUDA 后端与运行库怎么补齐、编译哪些 CPU 指令集变体、内存要开 EXPO 到什么频率、
线程给多少、上下文开多大、内存够不够、模型放哪、密钥怎么给、局域网怎么开——都已经调好并实测过。

> **一句话讲清取舍**：这套东西的优先级是**实用 + 快**，不是「能跑起来就行」。
> 所以默认就把能上显存的权重全部压上显存（实测只需约 **1.3 GiB** 显存即换来 **+52%** 生成速度），
> 把上下文上限卡在**显存装得下**的位置（3 GB 卡 32K / 8 GB 卡 64K / 16 GB 卡 128K），
> 目标是把生成速度顶到 **25 token/s** 一线 —— 标定卡 3 GB 已实测 23~24 t/s。

> ### 关于模型：套件与模型是分离的
>
> 下列性能数据是**当前验证过的实例**，不是项目的定义。换模型只需要两步：
> 换掉 `.gguf` 文件，改脚本里一行 `MODEL` 变量。
>
> | 当前实例 | `Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf`（MoE 架构，256 专家激活 8 个，**无 MTP**），Q4_K_XL 量化，20.82 GB |
> |---|---|
> | 为什么选它 | 35B 总参数 / 仅激活 3B 的 MoE 结构，在纯 CPU 上也能跑出可用速度；**无 MTP 头**，比带 MTP 的同规格模型快约 **14%**；同规格的其他 MoE 模型同样适用 |
> | 明确声明 | **本项目不再使用带 MTP 的模型** —— 实测带 MTP 的同规格模型即使不开投机也慢约 14%，开启投机更慢。下载请用 `unsloth/Qwen3.6-35B-A3B-GGUF` 仓（无 MTP），**不要**用 `...-MTP-GGUF` 仓 |
>
> 选型逻辑见下一节：**MoE 结构 + 内存带宽**才是这套东西成立的前提。

## 二、为什么核心是 Ryzen + DDR5（EXPO）

这一节解释项目的立足点。理解它，就能理解后面所有参数为什么是那样定的。

### 2.1 MoE 解码是内存带宽瓶颈，不是算力瓶颈

MoE（混合专家）模型每一层有几百个专家，但每个 token 只激活其中一小部分
（本机模型是 256 选 8）。这意味着：

- **真正参与计算的权重量很小** → 算术强度低，CPU 的向量算力根本吃不满；
- **权重必须从内存搬进来** → 瓶颈变成「内存能多快把权重喂给 CPU」。

用一句话概括：

```
生成速度 ≈ 内存带宽 ÷ 每 token 需要读取的字节数
```

所以这套方案围绕 **DDR5 内存带宽**，而不是围绕显卡或核心数。
这也是为什么调优的主线是「内存」而不是「算力」。

### 2.2 EXPO 是必开项，不是可选项

DDR5 插上主板后默认跑在 **JEDEC 4800 MT/s**。内存条本身的额定频率更高
（本机内存条是 DDR5-6000），必须进 BIOS **开启 EXPO** 才会跑到额定频率
（EXPO 是 AMD 平台的内存超频配置文件，等价于 Intel 平台的 XMP）。

从 4800 到 6000 是 **+25% 理论带宽**。在带宽瓶颈的解码阶段，这几乎是线性收益——
**不开 EXPO，等于白扔掉四分之一的速度**。

### 2.3 本机实测的硬件事实

| 项目 | 实测值 | 说明 |
|---|---|---|
| CPU | AMD Ryzen 9 9950X（Zen 5，16 物理核 / 32 逻辑核） | 命中 `ggml-cpu-icelake.dll`：AVX-512 + VNNI + VBMI |
| 内存容量 | 2 × 32 GB = **64 GB**，双通道（CHANNEL A / B） | 双通道是带宽翻倍的前提 |
| 内存条型号 | `CL36-48-48 D5-6000` | 即 DDR5-6000，CL36 |
| JEDEC 默认频率 | 4800 MT/s | 不开 EXPO 时就是这个 |
| **当前实际频率** | **6000 MT/s** | **EXPO 已生效** |
| 系统 | Windows 11 | |

### 2.4 怎么自查你的机器

**图形界面**：任务管理器 → 性能 → 内存 → 右下角「速度」。

- 显示 **6000**（或内存条额定值）→ EXPO 已开
- 显示 **4800** → 没开，去 BIOS 打开 EXPO / DOCP

**命令行**（PowerShell）：

```powershell
Get-CimInstance Win32_PhysicalMemory |
  Select-Object DeviceLocator, Capacity, Speed, ConfiguredClockSpeed, PartNumber
```

看 `ConfiguredClockSpeed` 是否等于内存条额定频率：`Speed` 列是 JEDEC 默认值，
`ConfiguredClockSpeed` 才是当前实际跑的频率。两者相等就说明没开 EXPO。

也可以直接跑本项目的 **`环境检查.bat`**，它会读取并显示内存容量与档位可行性。

### 2.5 三条只有在这类平台上才成立的实测规律

1. **24 线程在所有档位都比 28 线程快**。
   因为解码阶段内存带宽已经打满，再多的线程只是在抢同一根内存总线，
   反而增加争用与缓存失效。

2. **prefill（读提示）约 70 token/秒封顶**，与线程数和批大小基本无关
   （实测 16 线程 70.4 / 24 线程 68.6 / 32 线程 47.2 t/s；`--ubatch-size` 加大反而变慢）。
   读 21 GB 权重同样受带宽限制，不是加线程能解决的。

3. **生成速度取决于实际填充的上下文长度，而不是分配的 `-c` 值**。
   同样 16K 档位，短提示（33 token）能跑到 **16.06 t/s**。

### 2.6 换平台 / 不开 EXPO 会怎样

| 情况 | 影响 |
|---|---|
| 不开 EXPO（跑 4800） | 带宽直降约 20%，生成速度大致等比下降 |
| 只插单条内存 | 带宽腰斩，速度近乎腰斩。**双通道是硬性前提** |
| Intel 12/13/14 代消费级酷睿 | 不支持 AVX-512，自动回退 AVX2 变体，速度明显低于本表数值 |
| 支持 AVX-512 但无 VBMI 的 Intel（如 Cascade Lake 至强） | 需把 `ggml-cpu-cascadelake.dll.disabled` 改回 `.dll` |
| 换用小参数量的密集（非 MoE）模型 | 每个 token 要读全部权重，带宽压力成倍上升，速度大幅下降 |

> **换 CPU 不需要重新编译**。包里编译了全部 9 个 CPU 指令集变体，运行时自动择优。
> 但档位速度表与线程数需要按新 CPU 重测。

## 三、运行环境要求

| 项目 | 要求 |
|---|---|
| 系统 | Windows 10 / 11 **x64** |
| CPU | **AMD Ryzen 推荐**（本包在 Zen 5 上标定）。支持 AVX-512 更快，不支持会自动回退 AVX2 变体 |
| 内存 | **≥ 32 GB，强烈建议 2 条组双通道**（推荐 64 GB；默认档位需约 24 GB 可用内存） |
| 内存频率 | **建议开启 EXPO 跑到额定频率**（详见第二章） |

| 显卡 | **可选**：有 NVIDIA 独显时自动启用显存混合卸载提速（目标设备以 8 GB 为主）；核显与 A/I 卡按纯 CPU |
| 运行时 | **什么都不用装**。VC++ 运行库已随包附带，PowerShell / curl 系统自带 |

## 四、快速开始

### 第 1 步：拿到本包

方式 A —— 直接下载免安装包（推荐，已含编译好的程序）：

到 [Releases](../../releases) 页面下载 `...-no-model.zip`，解压到任意目录（**建议英文路径**）。
包内含全部程序与文档，但**不含模型**（20.8 GB），也**不含 CUDA 后端**（可选组件，见第十一节第 4 条）。

方式 B —— 克隆仓库：

```bat
git clone https://github.com/liuda1999/ryzen-ddr5-moe-deploy.git
```

### 第 2 步：双击启动（首次会自动引导下载模型）

双击 **`启动大模型.bat`**，首次运行会按顺序走：

1. **环境与安全检查** —— 10 项，有 `[失败]` 会直接阻止启动；最后一项报出显卡型号与显存；
2. **检查模型** —— `llama.cpp\models\` 下没有可用模型时，脚本会问你要哪个量化：

   ```
   1   IQ3_S     约 12.74 GB    32 GB 内存设备首选，速度略快
   2   Q4_K_XL   约 20.82 GB    默认推荐，量化质量最好
   ```

   选完先做**磁盘空间预检**，确认后开始下载：用系统自带 `curl` **断点续传**
   （中断后重跑脚本会接着下，不会从头再来），下完提示「下载完成，模型已就绪」，
   按回车继续。**已经有模型时整段跳过，直接进档位菜单**；
3. **选配置档位** —— 脚本按显卡显存推荐档位，直接回车即用推荐值（默认 16K 实用档）；
4. **是否开启深度思考** —— 直接回车 = 关闭（更快、更省 token）。

约 30~90 秒后显示「启动成功」并打印本次 API 信息，浏览器打开提示的地址即可对话。

> 想先手动下载模型也行，见第五节；启动脚本检测到已有模型会自动跳过下载步骤。
> **同一个脚本再运行一次就是关闭服务**（自动释放内存）。
> 想确认服务在不在：`启动大模型.bat status`。

### 第 3 步：NVIDIA 独立显卡自动加速（默认开启）

**默认已开启**，无需任何配置：有 N 卡就自动启用，没有就自动退回纯 CPU。

```bat
:: 平时什么都不用做（默认 GPU_MODE=auto）。
:: 想临时关掉做对比（不改文件）：
启动大模型.bat start 2 nothink nogpu
:: 想长期关掉：把 启动大模型.bat 顶部的 GPU_MODE 改成 off
```

启用后把「每 token 必读」的权重放进显存（**实测只需约 1.3 GiB**），
占总量 91.9% 的 MoE 专家权重仍留在内存。

> **本包在 GTX 1060 3GB（最低验证卡）上标定，目标设备以 8 GB 显存为主。**
> 显存越大，能搬上显存的**非专家权重 + 专家层**越多，生成速度越高：
> **8 GB ≈ 40 t/s、12 GB 50~60、16 GB 70~80（估测，现代显卡）**，并能跑 64K~128K 上下文。
> 4 / 8 / 12 / 16 GB 各档的配置与估算见
> [`参数阶梯手册.md`](参数阶梯手册.md) 的「不同显存容量怎么配」。

**GPU 加速需要两样东西，装了显卡驱动并不等于齐了**：

| 需要什么 | 说明 |
|---|---|
| NVIDIA 显卡驱动 | 机器上本来就有 |
| **CUDA 运行库**（3 个 DLL，≈770 MB） | **不随显卡驱动安装**，要另外获取。最省事是**复用本机已有的**——装过 CUDA / 跑过 PyTorch 的机器通常已有，加进 `PATH` 即可 |
| **CUDA 后端** `ggml-cuda.dll` | 从 llama.cpp 官方 Windows CUDA 预编译包取出，放进 `llama.cpp\build-zen5\bin\` |

跑一次 `环境检查.bat` 的第 **11 项「GPU 支持自检」** 会逐条告诉你缺什么、怎么补。

> ⚠️ 两个前提：**必须 CUDA 12.x**（13.0 起已不支持 Maxwell/Pascal/Volta 旧卡）；
> 后端 **API 版本须与本项目一致（当前为 3）**，否则会被拒绝加载并**自动退回纯 CPU**
> —— 安全失败，不会崩溃。
>
> 适用范围：**只针对 NVIDIA 独立显卡**。核显与 AMD / Intel 显卡一律按纯 CPU 运行。
> 原理、显存预算与旧卡注意事项见 [`参数阶梯手册.md`](参数阶梯手册.md) 的「GPU 混合卸载」章节。

命令与校验值见 [`下载模型.md`](llama.cpp/models/下载模型.md)。

> 内置下载只负责主模型；**mmproj 视觉投影需要手动下载**（0.84 GB，见上表）。
> 不下 mmproj 也能用，只是不能看图。

### 想换成别的模型？

**两个官方量化（UD-Q4_K_XL / UD-IQ3_S）无需任何配置** —— 启动脚本会自动检测
用得上的那个（Q4_K_XL 优先，IQ3_S 兜底），换个量化只要把文件放进 `llama.cpp\models\` 即可。

**换成完全不同的模型**才需要改 `启动大模型.bat` 顶部这一行（**注意保存为 ANSI 编码**，
或改 `_维护脚本\gen_toggle.py` 重新生成）：

```bat
set "MODEL=%ROOT%llama.cpp\models\你的模型.gguf"
```

选型建议：优先选 **MoE 结构**、量化后体积不超过可用内存的模型。
密集模型每个 token 要读全部权重，在纯 CPU 上会明显更慢（原因见第二章）。

## 六、配置档位（实测 + 按显存）

启动脚本会**按显卡显存自动推荐档位**（直接回车即用推荐值）。3 GB 那列为本机实测，其余为按显存可容纳权重与专家层的外推（**估测**）：

| 档位 | 上下文 | 推荐显存 | 3 GB 实测（短对话） | 约需内存 |
|---|---|---|---|---|
| **1 实用档** | **16K** | 无 N 卡 / ≤3 G | **23.7 t/s** | 24 GB |
| 2 长文档档 | 24K | — | 23.9 t/s | 24 GB |
| 3 超长档 | 32K | 4 G | 23.6 t/s | 25 GB |
| 4 长上下文档 | 64K | **8 G（主要目标）** | 23.9※ | 25 GB |
| 5 超大档 | 96K | 12 G | —（未实测） | 26 GB |
| 6 极限档 | 128K | 16 G | —（未实测） | 26 GB |

※ 64K 在 3 G 卡上需 KV 量化 `q8_0`（脚本会自动加）；≥4 G 用 f16。填满后 32K 约 20、64K 约 12 t/s。

> 生成速度与上下文长度几乎无关（填满之前）；无 N 卡时按纯 CPU 运行（短对话约 15.6 t/s）。

**不同显存容量的预期生成速度（估测）**：**8 GB ≈ 40 t/s、12 GB 50~60、16 GB 70~80**（显存越大，能搬上显存的专家层越多）。前提是**现代显卡**（RTX 3060/4060 级）；详见 [`参数阶梯手册.md`](参数阶梯手册.md) 的「不同显存容量怎么配」。

三条规律的成因见 [2.5 节](#25-三条只有在这类平台上才成立的实测规律)。

完整实测记录（含显存预算、模型对比、平台差异）见 [`参数阶梯手册.md`](参数阶梯手册.md)。

## 七、深度思考开关

选完档位后会问一次，**直接回车 = 关闭**。也可用命令行指定：

```bat
启动大模型.bat start 2 nothink    :: 关闭（默认）
启动大模型.bat start 2 think      :: 开启
```

同一个问题（「17×23=？」）、同一档位的实测对比：

| 模式 | 输出 token | 出结果耗时 |
|---|---|---|
| **关闭（默认）** | **4** | **约 0.3 秒** |
| 开启 | 241 | 约 15 秒 |

答案完全一样。差别只在要不要先把整段推理过程写出来——关闭后**省掉约 98% 的输出 token**。

> 服务端用的是 llama.cpp 的 `--reasoning off`，对 prompt 长度几乎无影响
> （实测 13 token vs 11 token），只影响生成阶段。
>
> 注意：这是 llama.cpp 的**服务端**开关，只对支持思考链的模型生效。
> 换成其他模型时该参数无副作用。

## 八、API 使用

服务是 **OpenAI 兼容**接口，端口固定为 **35035**（刻意避开 8080 / 8000 / 11434 等常用端口）。

| 用途 | 地址 |
|---|---|
| 网页对话控制台 | `http://127.0.0.1:35035` |
| OpenAI 兼容 API | `http://127.0.0.1:35035/v1` |

启动成功后窗口会打印**本次服务 API**（含地址与密钥），密钥同时复制到剪贴板。

```bat
curl -H "Authorization: Bearer <你的密钥>" ^
     http://127.0.0.1:35035/v1/chat/completions ^
     -H "Content-Type: application/json" ^
     -d "{\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}]}"
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:35035/v1",
                api_key="<你的密钥>")
```

**密钥填写要点**（这几条踩过坑）：

- 密钥存在项目根目录 `api-key.txt`，**每台机器首次启动自动生成**；
- 区分大小写，**不要加 `sk-` 前缀**，不要留空；
- 服务端**只认请求头**（`Authorization: Bearer`），**不支持** `?api_key=` 这种拼在 URL 上的写法；
- 客户端「模型名」留空或随便填即可（单模型服务）。

### 局域网访问

启动脚本默认 `HOST=0.0.0.0`，即局域网内其它设备可以访问（**需携带密钥**）。

```bat
:: 1) 以管理员身份运行一次，放行防火墙入站端口
开放局域网端口.bat

:: 2) 其它设备用局域网地址访问
http://<本机局域网IP>:35035
```

> ⚠️ **安全提示**：放行后，同网段**任何拿到密钥的设备**都能占用你的 CPU 和内存做推理
> （默认档位单次约 30 GB）。在咖啡厅、酒店等不可信 Wi-Fi 下，建议改成仅本机：
> 把 `启动大模型.bat` 里的 `set "HOST=0.0.0.0"` 改回 `set "HOST=127.0.0.1"` 后重启。
>
> 放行脚本用的是 `netsh advfirewall`，会对**所有网络配置文件**（域/专用/公用）生效，
> 且规则**不随项目删除而消失**，需要时用同一脚本的选项 2 撤销。

## 十一、已知限制

1. **仅 Windows x64**。脚本是 `.bat`，依赖 `cmd.exe` 与 PowerShell。
2. **首次对话可能很慢**。纯 CPU 时 prefill 约 70 token/秒（GPU 混合下约 170~200）；
   如果客户端注入了上万 token 的系统提示词或工具定义，光读提示就要几分钟。
   排查方法：看 `logs\` 里最新日志的 `n_tokens =` 数值。
3. **没有 N 卡时按纯 CPU 运行**。生成速度约 15.6 t/s，不适合高并发。
   （有 NVIDIA 独立显卡时**默认启用** GPU 混合卸载，见第四节第 3 步）
4. **GPU 混合卸载只支持 NVIDIA 独立显卡，且默认就开着**。核显与 AMD / Intel
   显卡一律纯 CPU。它需要用户自备 **CUDA 运行库**（3 个 DLL，≈770 MB，不随
   显卡驱动安装）；CUDA 后端 `ggml-cuda.dll` 二选一取得 —— 自编
   （`_维护脚本\build-cuda-backend.bat`，产物约 32 MB）或从 llama.cpp 官方
   预编译包取出。**公开发行包刻意不带它** —— 本项目编出的那一份只含
   sm_61（Pascal）机器码，放进公开附件对 Ampere/Ada 用户没用还占 30 MB；
   请按上面任一条自取。缺它时一律纯 CPU，不影响使用。
   收益已实测（GTX 1060 3GB / Pascal / 16K：15.6 → 23.7 t/s，**+52%**；填满上下文 +90%）；
   自动启用前会先**真跑一次后端设备枚举**，探不到就安静退回纯 CPU，不会拦启动。
   **默认策略刻意不留余量**（448 MiB 只是桌面 + KV + CUDA 上下文的硬开销）：
   标定用的 3 GB 卡是最坏情况，4 GB 及以上的卡本来就吃不满那约 1.3 GiB
   非专家权重（会被层数上限封顶），余量天然更大。只有 3 GB 卡同时跑重度
   图形程序时可能越界分页、把速度打回 1/2.4 —— 要留余量就调大 `GPU_RESERVE_MIB`。
   另外 `--fit on` **不能**与 `--cpu-moe` 同用（会让 llama.cpp 放弃适配后
   把全部层塞进显存），脚本已改为自己按显存算层数。
   顺带一提：本模型**无 MTP 头**；带 MTP 的同规格模型即使不开投机也慢约 14%，
   开投机更慢（22 → 10.5 t/s），故**本项目不再使用 MTP 模型**。
   **显存容量**：3 GB 是标定用的最低验证卡，目标设备以 **8 GB** 为主。显存越大，
   可把越多「专家层」也放上显存（每层约 498 MiB），生成速度越高 ——
   **8 GB ≈ 40 / 12 GB 50~60 / 16 GB 70~80 t/s（估测，现代显卡）**，上下文也能开到
   64K~128K。4 / 8 / 12 / 16 GB 的推荐参数与估算见
   [`参数阶梯手册.md`](参数阶梯手册.md) 的「不同显存容量怎么配」。
   ⚠️ **显存一旦超出就会暴跌** —— 实测 3 GB 卡多放 1 层（合计 3175 > 3071）时，
   生成速度从 23.9 崩到 **6.15 t/s**（WDDM 分页）。**宁可少放几层，也不能越界。**
5. **64K 及以上上下文（档 4~6）**：3 GB 卡上 f16 KV 放不下，脚本会**自动加 KV 量化
   `q8_0`**（短对话 23.9，填满后约 12.4 t/s）；**≥4 G 用 f16 KV 即可跑 64K**。
   96K / 128K 需要 12 / 16 G 显存，档位已留出但本机（3 G）未实测。
6. **单模型服务**。同时只服务一个模型，不排队、不调度。
7. **档位速度表是特定硬件实测值**。换 CPU、换内存频率、换模型量化级别后需重测。
8. **内置下载需要系统自带 `curl`**（Win10 1803+ 均有）。检测不到 `curl` 时脚本会
   跳过下载引导，改为提示按 [`下载模型.md`](llama.cpp/models/下载模型.md) 手动下载，
   不会卡住启动流程。
9. **中文路径可用，但仍建议英文路径**。llama.cpp 的 `--api-key-file` 打不开中文路径
   （本包已改为传密钥值而非文件路径来规避），且英文路径在第三方工具兼容性上更省心。
10. **内存带宽是天花板**。想再快，只能加带宽（换更高频 DDR5 / 上双通道双 rank），
   调线程或批大小已经到极限。
