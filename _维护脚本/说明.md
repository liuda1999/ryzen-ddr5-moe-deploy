# _维护脚本 目录说明

这里放的是**运维 / 开发用**的辅助脚本。日常使用完全不需要碰——日常只需要双击根目录的 `启动大模型_StartModel.bat`。

---

## 一、脚本生成器（改启动脚本时用）

| 文件 | 作用 |
| --- | --- |
| `gen_toggle.py` | 生成 `..\启动大模型_StartModel.bat`（二合一开关、**模型检测与内置下载**、档位、思考模式、API 展示） |
| `gen_check.py` | 生成 `..\环境检查_EnvCheck.bat`（11 项体检，第 11 项为 GPU 支持自检） |
| `gen_firewall.py` | 生成 `..\开放局域网端口_OpenLanPort.bat`（防火墙放行，需管理员） |

### ⚠️ 改 bat 的正确姿势

所有 `.bat` 都是 **GBK 编码 + CRLF 换行**，这是中文 Windows 命令行正确显示中文的前提。
**不要用记事本直接改 bat**（保存时容易被改成 UTF-8，导致中文全部乱码甚至括号解析崩溃）。

正确做法是改生成器再重新生成：

```bash
cd E:\llm-cpp
python _维护脚本\gen_toggle.py
python _维护脚本\gen_check.py
python _维护脚本\gen_firewall.py
```

三个生成器都基于脚本自身位置推导项目根目录，**在任何路径下调用都能正确工作**。

## 三、踩坑记录（改脚本前值得一读）

### 3.1 服务隐藏启动的三要点

服务要在后台**无窗口**运行，用的是「WScript.Shell 的 Run 方法 + 隐藏窗口风格(0) + 不等待(false)」。
这条命令有三个坑，都踩过一遍：

1. **整条 PowerShell 命令只用单引号 + `[char]34` 拼引号**，命令里不出现双引号，
   这样才不会被 cmd 的引号规则搅乱；
2. **`cmd /c` 后面的命令以引号开头时，必须在最外层再包一对引号**
   （脚本里就是 `$q + $q` 那一处）。否则 cmd 会把引号剥掉，命令直接报错、服务根本起不来；
3. **保留 `< nul`**：避免服务持有启动窗口的输入句柄，否则脚本会卡在最后的等待按键上。

另外，PowerShell 里拼接字符串时别多写引号——曾经因为一个多余的单引号，
让整条语句被包进字符串，PowerShell 报「字符串缺少终止符」。
排查这类"看不到输出"的启动失败，可以临时加 `2> "%ROOT%_ps_err.txt"` 捕获 stderr。

### 3.2 用管道喂输入做自动化测试时

Windows 的 `set /p` 从管道读输入有两个坑：

1. **行结束符必须是 CRLF。** 只给 LF（如 `printf '2\n'`）会让换行符混进变量值，
   下一句 `if "%TIER%"==""` 就报「命令语法不正确」并且脚本以 255 退出。
2. **`set /p` 会一次性读走管道里当前可用的全部数据。** 多步交互不能用一次性 `printf`
   喂完，否则后面的 `set /p` 读不到东西，只拿到默认值
   （表现为"明明输入了 y 却仍是 off"）。

正确写法是延迟分隔，模拟真人逐次输入：

```bash
{ printf '2\r\n'; sleep 2; printf 'y\r\n'; sleep 2; printf 'n\r\n'; sleep 2; printf '\r\n'; } \
  | ./启动大模型_StartModel.bat
```

> 普通用户双击运行不存在这个问题（键盘输入走控制台，逐行读取）。
> 这只影响用脚本 / CI 驱动 bat 的场景。

实测补充（本轮做模型下载流程全场景测试时确认）：

- **`set /p` 的行终止符是 CR（`\r`），不是 LF。** 输入文件只给 LF 时，`set /p`
  会把**整个文件**塞进一个变量（实测 `1\nn\n0\n` → 变量值 `1\nn\n0`），
  紧随其后的 `if "%X%"=="0"` 被换行拆散 → 报「命令语法不正确」。
  用 CRLF 文件则只读到一行（`1`）。
- **文件重定向比管道更可控**：`cmd //c "harness.bat" < in.txt`（Git Bash 下必须写
  `cmd //c`，写 `cmd /c` 会被 MSYS 把 `/c` 转成 `C:/c`，cmd 变成交互模式反而不读输入）。
  测试输入文件用 `printf '1\r\nn\r\n0\r\n'` 生成，别用 `\n`。
- 菜单类交互要留**轮次上限**兜底：输入耗尽（EOF）时 `set /p` 拿到空值会走默认项，
  可能反复回到菜单 → 必须「连续 N 轮无效输入就退出」，否则脚本场景会死循环。

### 3.3 环境变量可能让 Start-Process 直接报错

`Start-Process` 在环境里同时存在 `HTTPS_PROXY` 与 `https_proxy` 这类**大小写重复**的变量时，
会抛 `ArgumentException`（.NET 的环境变量字典区分大小写）。最终选用 COM 方式启动，
顺带规避了这类环境依赖。

### 3.4 在控制台里调用 llama-server 会把代码页改成 UTF-8（高危）

llama.cpp 的 `common_init()`（`common/common.cpp:390`）里有：

```cpp
SetConsoleOutputCP(CP_UTF8);
SetConsoleCP(CP_UTF8);
```

它改的是**当前控制台**的代码页。我们的 GPU 探测是在脚本所在的这个控制台里
跑 `llama-server --list-devices` 的，于是：

- 探测前 `chcp` = **936**，探测后 = **65001**
- 之后脚本用 GBK 写出的中文**全部变成乱码**，连 `pause` 的提示都会变成英文
- 重现方式（实测）：`chcp` → `llama-server --list-devices >nul 2>&1` → `chcp`

**规避**：每次在控制台里调用过 `llama-server` 之后立刻 `chcp 936 >nul 2>nul`。
两个生成器里都封装成了 `:CP_RESET` 子程序，探测后紧接着调用。

> 注意：正式启动服务不受影响 —— 它是用 `WScript.Shell.Run` 在**独立隐藏控制台**里
> 拉起的，碰不到脚本自己的控制台。只有"在前台跑一次 llama-server"才会中招。

### 3.5 `--fit` 与 `--cpu-moe` 不能同用（实测踩到，代价很大）

`--cpu-moe` 会设置「张量缓冲区覆盖」（`tensor_buft_overrides`）。而 `--fit` 一旦
发现用户已经设置过覆盖，就**直接放弃适配**：

```
common_params_fit_impl: projected to use 3036 MiB of device memory vs. 2208 MiB of free device memory
common_fit_params: failed to fit params to free device memory: model_params::tensor_buft_overrides already set by user, abort
```

放弃之后 `n_gpu_layers` 落到「全部层」，于是 **42/42 层全塞进显存**、
需求 3036 MiB 对可用 2208 MiB，WDDM 只能把显存分页到系统内存 ——
实测生成速度从 14.6 t/s 掉到 **6.1 t/s**（1/2.4）。

所以启动脚本的 `auto` 策略**不用 `--fit`**，而是自己按显存算层数：

```
N = (显卡总显存 - GPU_RESERVE_MIB) / GPU_LAYER_MIB
```

另外两个相关实测结论：

- **按总显存算，不要按空闲值算。** llama.cpp 报的 `free` 额外扣了一份保留量
  （GTX 1060 3GB 报 2460 MiB，实际可用约 2880 MiB），用空闲值会少卸好几层。
- **`-nkvo` 会让收益归零**：卸载后每个 token 都要把 KV 经 PCIe 搬回 GPU，
  实测 19.3 → 14.9 t/s（回到纯 CPU 水平）。小显存卡也要让 KV 留在显存。

### 3.5.1 两个默认值（2026-10-15 晚定稿，改前先看这里）

- **`GPU_MODE` 默认是 `auto`**（不是 `off`）。它不是「无条件启用」，而是
  「探测通过才启用」：先真跑一次 `llama-server --list-devices`，这一步会实际
  加载 CUDA 后端与运行库，成功才拼 GPU 参数；任何一环失败都安静退回纯 CPU。
  第 10 项自检与第 11 项自检**永不设 `[失败]`**，不会因为显卡的事拦启动。
  改这个默认值前请确认上面这条兜底链没被破坏。
- **显存「压满、不留余量」是刻意的**：`GPU_RESERVE_MIB=448` 是
  「桌面 + KV + CUDA 上下文」的硬开销，不是安全垫。3 GB 卡是标定用的最坏情况，
  4 GB 以上的卡本来就吃不满那约 1.3 GiB 非专家权重（被 `GPU_NLAYER` 封顶）。
  调小它也不会更快（32 层往上速度就持平了）。

### 3.6 换模型要连带改的三处（本轮换无 MTP 模型时踩到）

换 `.gguf` 时除了改 `MODEL`，还有三处硬编码要同步，否则会误报：

1. `gen_toggle.py` 第 4 项自检的「模型应约 XX GB」文案（按 GiB 比较）；
2. `gen_check.py` 里的同款文案；
3. `GPU_LAYER_MIB` / `GPU_NLAYER` —— 前者≈「非专家权重总量 ÷ 层数」，后者=层数。

另外记录一条**选型结论**：本机（GTX 1060 3GB）实测，**带 MTP 头**的同架构模型
即使不开投机也慢约 14%（21.0 vs 23.7 t/s），**开启** `--spec-type draft-mtp`
更慢（掉到 10.5 t/s）。故默认模型选**无 MTP** 版；多模态投影（mmproj）对文本速度
无影响（挂/不挂无差异）。

### 3.5.2 `REM` 后面必须跟空格

写注释时别写成「REM 紧跟全角括号或反引号」的形式（例如 REM 后直接写「（」）。
cmd **不把这种写法当注释**，会把整行当命令执行 —— 表现为启动成功信息里凭空多一行
`'REM（…' 不是内部或外部命令`。全量自检：

```bash
# 找 REM 后没空格的注释（纯 REM 行是正常分隔线，不算）
grep -nP '^\s*REM(?![\s])' *.bat
```

### 3.7 `chcp` 会读走并清空标准输入（实测，影响面很大）

改代码页时必须给它一个空输入，否则 `chcp` 会去读 stdin 并把它清空：

```bat
chcp 936 <nul >nul 2>nul
```

不加 `<nul` 时，用重定向/管道喂输入的场景里**第一行输入会被吃掉**（表现为
「明明喂了 2，脚本却按默认值走」）；交互使用时则会把**检查期间提前键入的内容**
一并吞掉（用户以为已经输入，脚本却当没看见）。`启动大模型_StartModel.bat` 与
`环境检查_EnvCheck.bat` 的文件头、`CP_RESET` 处都已改成这个写法。

> 排查方法：写一个最小 bat，`chcp 936 >nul` 与 `chcp 936 <nul >nul` 各跑一遍，
> 后面接 `set /p` 看能否读到输入。实测前者读不到、后者正常。

### 3.8 `if ( ... )` 块里的 `%VAR%` 是在「块解析时」展开的

cmd 会把整个括号块当成**一条命令**先解析再执行，块内的 `%VAR%` 全在块开始执行前就展开完了。
于是下面这种写法是错的：

```bat
if "%NEED_ASK%"=="1" (
  set "YN="
  set /p "YN=继续吗(y/N): "
  if /i not "%YN%"=="y" goto :CANCEL     REM ← %YN% 是进入块之前的旧值（空）！
)
```

实际表现：**用户输 `y` 也永远走取消分支**（因为 `%YN%` 早在 `set /p` 之前就展开成空字符串了）。
同理，块内 `set` 的变量在块内回显也会是旧值（曾表现为检查项显示「大小  GB」，数字是空的）。

**修法**：把「读输入 + 判断」抽成一个 `call :SUB` 子程序 —— 子调用是全新的解析上下文，
`%VAR%` 在子程序里是执行时展开；回显类逻辑同理，或者改用 `setlocal EnableDelayedExpansion`
配合 `!VAR!`（本项目未全局开启延迟展开，避免影响含 `!` 的文本）。

**静态自检脚本**（防复发，直接跑）：

```python
import re
raw = open('启动大模型_StartModel.bat','rb').read().decode('gbk', errors='replace')
lines = raw.split('\r\n'); depth = 0; block = []; issues = []
def scan(block, start):
    defined = set()
    for _, ln in block:
        for m in re.finditer(r'\bset\s+(?:/p\s+)?\"?([A-Za-z_]\w*)=', ln):
            defined.add(m.group(1).upper())
    used = {}
    for i, ln in block:
        for v in re.findall(r'%([A-Za-z_]\w*)%', ln):
            used.setdefault(v.upper(), i)
    for v in sorted(defined & used.keys()):
        issues.append((start + 1, v, used[v] + 1))
for i, ln in enumerate(lines):
    o = ln.count('(') - ln.count(')')
    if depth == 0 and o > 0:
        block = [(i, ln)]; depth = o; start = i
    elif depth > 0:
        block.append((i, ln)); depth += o
        if depth <= 0:
            scan(block, start); depth = 0
print('问题数:', len(issues), issues)
```

> 注意：正则要覆盖 `set /p "VAR=..."` 形式，否则会漏掉输入类变量（本轮就是先漏了 `YN`）。

### 3.9 生成速度突然掉到 8\~9 t/s —— 一次完整排查（2026-10-16）

**现象**：同一台机器、同一份配置（32K 档 / `-ngl 40 --cpu-moe` / 24 线程 / f16 KV / mmproj），
某次运行只有 **8.2 t/s**，重启后立刻稳定 **21\~23 t/s**；两者的启动日志与命令行**逐字相同**。

**已逐项实测排除**（全部为可复现的对照实验）：

| 假设 | 实测结果 | 结论 |
| --- | --- | --- |
| 上下文太长 | 那个实例在 **287 token** 的短上下文下也只有 7.84 t/s；本机 28\~13831 token 均为 21\~23 t/s | 排除 |
| thinking 开关 | nothink 21.33 / think 22.10 t/s | 排除 |
| 显存超额（WDDM 分页） | 快慢两态显存分布几乎相同（专用 \~2550 + 共享 \~1300 MB） | 排除 |
| 磁盘换页 / 内存不足 | 慢态 `Memory\Pages/sec ≈ 0`、可用内存 28.8 GB、模型全在缓存（standby 24 GB） | 排除 |
| GPU 被别的程序抢 | 开 5 个动画窗口把 GPU 压到 50%+、显存 2919/3072 → 仍 **23.26 t/s** | 排除 |
| DRAM 带宽被抢 | 后台 28 GB/s 内存拷贝 → 生成只降 **7%**（prefill 才明显降） | 排除 |
| CPU 被限频 | `PROCTHROTTLEMAX=50`（有效频率 51%）→ 生成仅 19.59 t/s（**-11%**） | 排除 |
| 电源计划 / EXPO / 硬件 | 高性能计划、EXPO 6000 生效、无 WHEA 与热节流事件 | 排除 |

**关键判据**（比"慢"本身更有信息量）：

- 慢态：prefill **78 t/s**（正常 128\~190）、生成 **8.2 t/s**（正常 21\~23）——两个阶段同时退化；
- 慢态下 llama 占满 24 线程，但 **GPU 在挨饿**：显存带宽占用 10%、功耗 49.6 W；
  健康时应为 26\~29% / 70 W。
- 即瓶颈落在**单 token 的 CPU↔内存/GPU 关键路径**上，且与「显存、上下文、主频」都无关。

**处置**：**重启服务即恢复**（本次重启后立刻回到 21\~23 t/s）。再遇到时先跑
`python _维护脚本\diag_speed.py` 抓现场——脚本会打印生成速度、CPU 有效频率、内存分页、
GPU 功耗与显存构成、以及抢占 CPU 的其它进程，与本节基线对照即可判断是机器侧还是配置侧。

> 顺带确认的正常基线（GTX 1060 3GB，32K 档）：
> 短提示生成 **21\~23 t/s**；13K 提示 prefill **128\~130 t/s**、生成 **21.2 t/s**。

### 3.10 显存预算怎么算（0.2.6 起，全部实测标定）

先在 GTX 1060 3GB 上做了「层数 × 显存 × 速度」扫掠（32K / `--cpu-moe` / 24 线程）：

| -ngl | 专用显存 | 共享（host-mapped） | 生成 |
| --- | --- | --- | --- |
| 0 | 1535 MB | 112 MB | 13.75 t/s |
| 16 | 2397 | 302 | 17.18 |
| 24 | 2659 | 366 | 17.80 |
| 32 | 2612 | 750 | 19.50 |
| 40 | 2619 | 1198 | 20.50 |

三条要紧的结论：

1. **专用显存被驱动封顶**（≈2620 MB = 总量 − 其它程序 − 驱动保留），超出的权重进 host-mapped
   共享内存、每 token 走 PCIe。所以预算要算准，算多了就有一部分权重长期走 PCIe。
2. **那约 1.2 GB「进内存」的权重主要是视觉塔（mmproj）**，而且**不拖慢文本生成**
   （带 20.46 / 不带 20.44 t/s）。想给它腾地方就把顶部 `MMPROJ_SW` 设成 `off`。
3. **能省的是 KV 精度**：32K 的 f16 KV ≈655 MiB，q8_0 ≈327 MiB，速度损失约 0.7%。
   所以默认策略是「q8_0 能多装 2 层以上就换」。

当前公式（`gen_toggle.py` 的 `GPU_*` 常量）：

```
可给权重 = 总量 − 其它程序占用 − 计算缓冲/CUDA上下文(480) − 视觉塔(320, 载 mmproj 时)
           − KV(上下文/50 或 /100) − 安全垫(默认 128)
层数     = 可给权重 ÷ 40 MiB，上限 41（=模型层数）
```

启动信息里会把这套账**逐项打印**，便于核对。Windows 没有「锁定显存」的公开接口，
能做的就是「算准 + 留安全垫 + 告诉你是谁占了」。其它程序占用 > 600 MiB 时会告警。

> 安全垫调大 = 更保险但少装几层（每层 40 MiB）；调小则相反。别设成 0。

### 3.11 脚本双语与两个新坑（0.2.6）

三个 .bat 的**用户可见输出**（332 行）已改为「中文 / English」。改动方式是
在生成器上做整行映射替换（见 `_tmp` 时期的做法，已并入生成器源码），
`_维护脚本\check_bat.py` 负责回归检查。两条经验：

1. **GBK 不允许的字符**：第一版预算文案里用了 Unicode 减号 `−`(U+2212)，
   生成时直接 `UnicodeEncodeError`。写文案只用 ASCII 的 `-` 或全角符号。
2. **括号块内展开出括号 = 上机才炸**：英文文案里写了 `(41 layers)`，而该 echo 位于
   `if ( )` 块内 —— 展开出的 `)` 提前闭合了块，报「此时不应有 experts」，
   纯静态的括号平衡检查**发现不了**。修法：这类长文案改成**块外打印**（用单行 `if defined`），
   并让 `check_bat.py` 扫描「块内被 echo 的变量 ∩ 取值含半角括号」。

### 3.12 网页端提交是「签名提交」，本地补不回来（2026-10-16 踩到）

**现象**：在 github.com 上点“Edit file”改 README 之后，本地 `git log` 只剩最近一两条，
`git rev-parse HEAD^^` 报 `fatal: Failed to traverse parents of commit ...`。

**原因**：网页端提交由 GitHub 用 **web-flow 密钥 GPG 签名**，提交对象里有 `gpgsig` 头：

```
tree 4795abb6...
parent 19a88d56...
author 刘鸿祥 <...> 1792090885 +0000
committer GitHub <noreply@github.com> 1792090885 +0000
gpgsig -----BEGIN PGP SIGNATURE-----
 
 wsFcBAABCAAQBQJq0SMF...
 ...
 -----END PGP SIGNATURE-----

Update README.md
```

签名是对象的一部分，**没有签名就凑不出同一个 SHA**。而 API 的
`commit.verification.payload` 是 GitHub **重新序列化**的文本（不含 `gpgsig`）、
`signature` 也不保证与对象内一字不差 —— 实测把两者拼回去，哈希对不上（枚举了缩进/换行多种形态）。

**所以**：这类提交只能靠 `git fetch` 取。`pull_via_api.py` 会识别出来并明确提示，
不会让你看到一句莫名的失败；它能补的是**未签名提交**（比如自己用 `push_via_api.py` 推上去的那些）。

**顺带一个教训**：`push_via_api.py` 里那条「远端分歧预检」原本硬依赖 `HEAD^^`，
本地一断层就直接退出。已改为：取不到 `HEAD^^` 就**跳过预检**，但仍以
「新建树哈希 == 本地 HEAD 树」把关 —— 把关点没降级，只是不再要求本地历史完整。

> 想让本地历史补全：在**能访问 github.com 的网络**里执行一次 `git fetch origin`。
> 本沙箱到 `github.com` 不通（只放行了 `api.github.com` / `uploads.github.com`），
> 所以这条只能你自己在终端里跑。

### 3.13 echo 正文里的 `<` `>` 是重定向符，会把整个批处理打断（2026-10-16 踩到）

**症状**：`status` 输出到尾部的「访问密钥」那行时，突然打印 `命令语法不正确。`，
**然后整个批处理直接中止**（退出码 255），后面的菜单再也显示不出来。

**原因**：双语化时把英文文案写成了

```
echo   调用方式/USE    请求头加 Authorization: Bearer 上面这串密钥 / send header: Authorization: Bearer <key above>
```

那个 `<` 被 cmd 当成**输入重定向**，`>` 当成输出重定向，整条 `if defined API_KEY ( ... )` 复合语句
解析失败 → 报错并**终止整个批处理**（不是跳过这一行）。这类错误的连带后果比想象的大：
该行所在子程序一崩，调用它的菜单分支就整段失效 —— 表现为「运行中双击脚本毫无反应 / 开关失灵」。

**修法**：正文里的尖括号要转义成 `^<` `^>`。同类字符还有 `|` `&` `(` `)`。
`check_bat.py` 已加对应扫描：剥掉行尾合法重定向（`>nul 2>nul` 之类）后，正文里还剩 `<` `>` 就报错。

> 记一条判据：**只要某条语句的正文里出现未转义的 `<` `>`，就别指望它只是「显示不对」——
> 它会连累整个脚本停摆。**

### 3.16 正文里的一对 `~` 会被 GitHub 渲染成删除线（2026-10-16 踩到）

**症状**：README 里那段「关键做法」在网页上**大部分文字被一条横杠划掉**，本地 Markdown 却看不出问题。

**原因**：GitHub 的 GFM 里，**一对单波浪号**就会包成 `<del>`（不是必须写两个）。那段里有两个：

```
装不下 30B~35B 的全部权重……（约 13~16 t/s）
        ↑ 第一个                    ↑ 第二个
```

两个 ~ 之间的一切都被划掉。用 GitHub 的渲染接口实测确认（这个判据比查文档可靠）：

```python
POST https://api.github.com/markdown   {"text": "...", "mode": "gfm", "context": "owner/repo"}
#   "30B~35B……13~16 t/s"    -> <del>35B……13</del>   ← 被划掉
#   "30B\~35B……13\~16 t/s" -> 正常显示 ~
```

**修法**：正文里的 `~` 一律转义成 `\~`。**代码块与行内代码里不要转**（那里不解析标记）。

**影响面**：全仓有 **120 处**（10 个文档），一次性全部转义。`check_docs.py` 负责回归：
按「段落 / 表格单元格」统计**未转义**的 `~`，出现 ≥2 个就报错 —— 注意要按容器算，
一行里塞两个同样会出问题（第一版按行数判断，漏掉了这种）。

> 顺带记一条：**这类排版 bug 本地编辑器看不出来，只有 GitHub 的渲染结果算数。**
> 拿不准就用上面那个 render 接口验一遍。
