## 0.3.10 — 修分发包校验误报：模型不再是「包完整性」判据

> 纯维护版本。**运行时代码、启动脚本、预编译二进制、参数档位一个字节都没改**，
> 不需要重新标定速度，也不需要重新下载模型。
> 起因是有用户反映 GitHub 上的部署包存在问题；逐层排查后确认包本体没坏，
> 坏的是「分发包清单 + 校验脚本」这条验收链路。

### 问题

从 Releases 下载的 `...-no-model.zip` 解压后，按清单运行
`python _维护脚本\verify_package.py`，必然得到
「结论：分发包不完整，建议重新拷贝」并返回 1。原因有三层：

1. 清单把两份模型列为**必需**，但 no-model 包本来就不含模型。
2. 清单记的是【本机早期模型文件】的大小，与官方发布值不一致：

   | 文件 | 清单旧值 | 官方发布值 | 差 |
   |---|---|---|---|
   | Q4_K_M | 21,233,608,512 | 22,134,528,992 | 900,920,480 B（约 859 MiB） |
   | mmproj | 902,822,528 | 902,822,624 | 96 B |

   所以即使按 README 下载了正确的官方模型放进去，也会被判「大小不符」。
3. 清单【2】/【4】分节条件重叠，`下载模型.md` 被写进两节、校验两次
   （声明 69 个文件，实际解析出 70 行）；本机没放 IQ3_S 还被列进
   「【!】未找到，请确认」的告警段，看起来像缺件。

### 改了什么

| 文件 | 改动 |
|---|---|
| `_维护脚本/model_catalog.py`（新增） | 官方模型精确字节数的**唯一事实源** |
| `_维护脚本/make_manifest.py` | 模型行改用官方值且全部标 `*`（可选）；分节改用显式条目，去掉重复与误报 |
| `分发包清单_PackageManifest.txt` | 重新生成：70 行 = 70 个唯一路径，模型 3 行为不随包分发的参考值 |
| `_维护脚本/verify_package.py` | 模型不参与包完整性判定：缺失只提示、版本不同给 `[提示]`、只拦不足官方值一半的明显截断；**随包文件仍严格做大小 + SHA256 校验** |
| `_维护脚本/check_manifest.py`（新增） | CI 门禁：交叉核对清单 / catalog / 启动脚本 `DL_BYTES` / 生成器 / `下载模型.md`，并检查无重复条目与随包文件哈希 |
| `.github/workflows/static-checks.yml` | 接入上面的门禁（共 8 步） |

一个实现上的坑：`mmproj-BF16.gguf` 官方只有约 0.84 GiB，
所以「小于 1 GiB 即截断」会把合法文件误判成损坏 —— 最终改用
**不足官方值 50%** 的相对阈值，并由 CI 核对两处阈值一致。

### 校验结果

- 静态门禁 8 步在 GitHub Actions 全绿（run #42859136501）
- 仓库侧 `verify_package.py`：一致 67 / 异常 0 / 缺失 0 → **分发包完整，退出 0**
- 全新解压的 no-model 包内运行：三个模型 `[未带]` → **分发包完整，退出 0**
- 行为矩阵 4 场景（模型缺失 / 版本不同 / 明显截断 / 随包文件被篡改）全部符合预期
- 生成的 `启动大模型_StartModel.bat` 与入库文件 SHA256 完全一致

### 升级方式

直接下载本版 `...-no-model.zip` 覆盖即可（**模型文件不会被动到**）。
旧包里的 `分发包清单_PackageManifest.txt` 与 `_维护脚本\verify_package.py`
请一并覆盖。运行时与 0.3.9 完全相同，无需重新标定。

P2 级体验项（zip 无顶层目录、包内维护脚本依赖 `.git`、Windows 内置解压
对中文名的兼容性）本版未处理，不影响使用。
